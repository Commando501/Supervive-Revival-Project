======================================================================

CLAIM UNDER TEST: a pushed {"Resource":X,"Version":N,"Payload":""} frame makes the
client re-issue the HTTP GET for X, with NO socket teardown.

EXPERIMENTAL DESIGN — picking an attributable observable
--------------------------------------------------------
First measured which resources are POLLED vs RESYNC-ONLY, because a fetch after a
push proves nothing if the client was going to fetch anyway. Over a 10-minute window:

  /mailbox/config          POLLED every ~90s      -> unusable as a signal
  /progression/players     3 moments only         -> resync-only
  /inventory/players       3 moments only         -> resync-only
  /mmr/player-ratings      3 moments only         -> resync-only
  /match-history/players   3 moments only         -> resync-only
  /party/parties           3 moments only         -> resync-only

Those three moments were 03:53:13, 03:53:15 (two ags-restart reconnects) and
03:58:50 (a deliberate admin drop). i.e. they fire ONLY on a messenger resync.
A fetch with the connect-count unchanged is therefore unambiguous.

RESULT A — /match-history/players, Version 7                        ★ CONFIRMED
--------------------------------------------------------------------
  push  04:06:31
  GET   04:06:31.491   <- 491 ms later
  messenger connects: 3 -> 3   (NO reconnect)
  prior fetches of this resource: only the 3 resync moments
=> One pushed frame caused a targeted client refetch with the socket kept up.

RESULT B — /party/parties/party-<id>, Version 3                     IGNORED
--------------------------------------------------------------------
  no fetch at all. NOT a mechanism failure — the version gate working.
  partyVer is seeded `time.Now().UnixMilli()` (~1.76e12, store.go:141), so the
  client had long since cached a vastly larger version and 3 could not beat it.

RESULT C — /party/parties/party-<id>, Version = now-millis      ⚠ REFETCH LOOP
--------------------------------------------------------------------
  push  04:10:49
  GET   04:10:49.156, .270, .323, .388, .454, .521, .587, .658, ... 
  46 fetches in ~4 s (~one per 70 ms) and NOT self-limiting.
  messenger connects: 3 -> 3 (so the mechanism is confirmed a second time —
  but pathologically).
  CAUSE: pushed version > the version buildSoloParty actually serves. The client
  caches the pushed value, refetches, receives a LOWER version, still considers
  itself stale, and asks again forever.
  CLEARED BY: restarting ags, which reseeds partyVer = now-millis (1786612281493)
  above the poisoned cache (1786612248814). Post-restart: 1 fetch, no loop.

THE RULE THIS ESTABLISHES
-------------------------
Pass the version the HTTP document will carry — NEITHER MORE NOR LESS.
  too low  -> silently ignored, and the null is indistinguishable from
              "the client does not handle this resource"
  too high -> unbounded refetch loop
The shipped lever is correct by construction: notifyPartyResources() passes
interactive.Service.PartyVersion(), the same counter buildSoloParty is served with.
The loop above was caused by a MANUAL probe using a wall-clock value instead.

WHAT IS AND IS NOT PROVEN
-------------------------
PROVEN: a pushed version bump causes a targeted refetch, no teardown, sub-second.
NOT PROVEN: that the client APPLIES the refetched party document. S85 measured the
avatar card applying during the messenger-RECONNECT resync; the apply may be bound
to the connection-state-changed broadcast rather than to a fetch completing.
=> lobby.enableTargetedResync ships DEFAULT OFF. Flipping it needs one live check:
   set it true, change an avatar, confirm the CARD updates (not merely that
   GET /party/parties appears — that half is already proven above).

THE FIX TO THE PREVIOUS ATTEMPT: pick an observable the shim CANNOT touch.
  loadout_fix.cpp calls exactly three setters — SetHeroCosmeticsBundlePreference,
  SetLuxeSkinChromaPreference, SetSlotCosmetic — and it polls /revival/loadout
  every ~175 ms. So ANY skin/slot change is applied by the shim within ~200 ms
  and cannot discriminate. `grep -ci lobbyplatform loadout_fix.cpp` = **0**, while
  loadout.go:411 puts `lobbyPlatformPreference` INSIDE the party document.
  => the LOBBY PLATFORM (the podium under the hunter) is carried by the party doc
     and is invisible to the shim. That is the clean observable.

DESIGN — state change and push were separated on purpose:
  handleSetLobbyPlatform (interactive.go:247) bumps LoadoutVersion but does NOT
  call markLoadoutDirty. So changing the podium changes BACKEND STATE ONLY and
  fires no push — giving a free control arm. The push was then triggered
  separately with a no-op slot write (slot "FK15Probe", empty asset => deletes a
  key that does not exist), which reaches markLoadoutDirty and carries the real
  PartyVersion().

THE ROUND-TRIP (operator-confirmed screenshots)
  A  podium CYAN/BLUE   backend already LobbyPlatform:Collector, NO push fired
                        TARGETED RESYNC 3, GET /party/parties 3
     => a backend change alone moves nothing. Client provably unaware.
  B  podium GOLD        push fired: TARGETED RESYNC 3->4, /party/parties 3->4
     => refetched AND APPLIED.
  C  podium CYAN/BLUE   reverted to Starter + push: RESYNC 4->5, parties 4->5
     => applied again, in reverse.

  Throughout: messenger DROP = 0, connects = 1, socket uptime continuous.
  BLUE -> GOLD -> BLUE on command. No rendering coincidence or reading error
  produces that sequence.

CONCLUSION
  A targeted per-resource version bump on the messenger causes the client to
