S110 TASK ONE -- PREDICTION REGISTERED BEFORE THE TUTORIAL SITTING
written 2026-08-05, before item_watch.py was pointed at a live tutorial run

Basis (all measured read-only at the menu earlier today, docs/s110-itemwatch-*.log):
  * "Unreachable" is NOT a sticky bit in this build. Reachability is an alternating low-bit flag:
    the whole population swaps which of bits 0/1/2 it carries on each GC pass (observed 0x2 -> 0x1
    -> 0x4, 232/256 controls flipping inside one 250 ms sweep, passes ~61 s apart, matching the
    game's own gc.TimeBetweenPurgingPendingKillObjects = 61.1).
  * Rooted and marked are MUTUALLY EXCLUSIVE in the natural population:
        rooted     4915 objects, of which     6 (0%)   carry the current reachability flag
        not rooted 17237 objects, of which 17234 (100%) carry it
    So a root-set object is EXCLUDED from marking; it is not marked, it is skipped.
  * Therefore the shim's GcRoot poke (InterlockedOr of bit 30 onto an object that already carries a
    reachability value, flags 00000004 -> 40000004) produces a state that occurs in 0.03% of the
    natural population: ROOTED **and** MARKED at once.

PREDICTIONS, in order of confidence:

  P1  The run AnimSequence will be acquired in state ROOTED+MARK (the chimera), not ROOTED.
      Falsified if the shim's poke leaves it looking like the other 4,915 rooted objects.

  P2  It will die by discriminator B or A -- item.Object -> 0 (FreeUObjectIndex ran), possibly
      followed by the slot being reissued. I.e. REAL destruction, not an out-of-band overwrite.
      Falsified by D: the object's vtable/NamePrivate going bad while the array slot is untouched.

  P3  The death will be concurrent (within ~3 s) with a visible GC pass -- a reachability-flag flip
      and/or a live-count drop. Falsified if the object dies in a window with no GC activity at all,
      which would mean something tore it down specifically.

  P4  Between the poke and the death, the object will FAIL to acquire the new reachability flag at
      the next flip (state ROOTED+MARK -> ROOTED, or -> UNMARKED), because rooted objects are not
      marked. If it goes UNMARKED (bit 30 lost) that would mean the poked bit was CLEARED by the
      engine, which is a different and stronger finding than "the bit is ignored".

  Explicitly NOT predicted, and to be read off the data rather than assumed: whether the poked bit
  is honoured. P4 distinguishes "ignored" from "cleared"; neither is assumed here.

VOID conditions registered in advance:
  * the target is never acquired (no anim load line in the marker)  -> the run measures nothing
  * zero target events AND zero decoy events                        -> the watcher is unproven, VOID
  * the game dies before the anim loads                             -> not a data point
