================================================================================================
1. THE TWO ARMS, AND WHY BOTH FLY IN ONE WINDOW
================================================================================================
ARM A  poke CDO(AIControllerClass).bWantsPlayerState = 1, THEN spawn.
       DEPENDS ON AN UNVERIFIED FACT: that UE copies the CDO's property block onto a new instance
       AFTER the class constructor runs. AAIController's ctor CLEARS this bit on every instance
       (0x45D19AD `and ecx,~0x20`), and the consumer reads the INSTANCE, not the CDO. S130's
       bCanEverReplicate precedent does NOT establish this -- its consumer read the CDO DIRECTLY
       (`cmp byte [CDO+0x6C],0`). This arm MEASURES the propagation rather than assuming it.
ARM B  spawn normally, then call InitPlayerState DIRECTLY on the controller. Needs no poke and no
       propagation. Dispatched THROUGH THE VTABLE and REFUSED unless [[ctl]+0x888] resolves to RVA
       0x36DEE20 (it matters: [M] ALokiPlayerController's slot 273 is the void fold).

CONTROL: WITHIN-RUN. Spawn #1 runs with the bit CLEAR and spawn #2 with it SET, same world, same
instrument, milliseconds apart. The ONLY difference is one bit on one CDO. ARM B then runs on
controller #1, whose PlayerState has already been printed as NULL.

2. PREDICTIONS -- written before the flight
================================================================================================
P1  The CDO's bWantsPlayerState reads CLEAR at baseline (L1). Stock UE clears it in the ctor, so
    a SET here would mean something else already changed it and the whole framing is wrong.
P2  Spawn #1 (CONTROL) reproduces S136 exactly: controller created, its bit reads CLEAR (L2),
    ctl.PlayerState NULL (L3), pawn.PlayerState NULL (L4).
P3  The poke lands and readbacks: CDO byte gains exactly bit 0x20, dword delta == 0x20 exactly
    (no neighbouring bit moves).
P4  ARM A, IF the CDO value propagates: spawn #2's controller reads bit SET (L2), ctl.PlayerState
    NON-NULL (L3), AND pawn.PlayerState NON-NULL (L4) -- both, because InitPlayerState runs inside
    PostInitializeComponents, i.e. BEFORE SpawnDefaultController calls Possess -> PossessedBy ->
    APawn::SetPlayerState, which is what copies it across.
P5  ARM A, IF it does NOT propagate: spawn #2's controller reads bit CLEAR (L2) and PlayerState
    NULL. That REFUTES the CDO-poke route as stated and is a real, reusable result, not a failure.
P6  ARM B success signature is DIFFERENT from ARM A's and cannot be confused with it:
    ctl.PlayerState NON-NULL and pawn.PlayerState STILL NULL -- possession already happened and
    nothing re-runs SetPlayerState.
P7  The PlayerState-chain census (corroborator) moves by +1 per controller that gains one, and the
    A0==A1 stability re-scan holds with no call in between.
P8  =BotController-chain stays 0 throughout. This does NOT produce a Loki bot and must not be
    written up as one.

================================================================================================
3. WHAT WOULD MAKE THE SITTING VOID OR UNINTERPRETABLE
================================================================================================
V1  `[BS] done` never appears, or `called=0`. S136's flight 1 showed a clean 0/0/0 census under a
    confident VERDICT line and was a NO-OP. A census delta with called=0 is UNINTERPRETABLE.
V2  The A0/A1 stability re-scan MOVES with no call in between -- something else is spawning.
V3  No controller on either pawn: SpawnDefaultController did not run, so the gate was never
    reached. Says nothing about bWantsPlayerState.
V4  The PRECONDITION line reports PlayerStateClass NULL. InitPlayerState then logs its own error
    and bails, and a null PlayerState is attributable to that, not to the poke.
V5  BOTH controllers end up with a PlayerState, including the one spawned with the bit clear. The
    control is then broken and the poke is not what produced it.
