================================================================================================
0. WHAT IS BEING TESTED, AND WHY IT IS THE WHOLE POINT
================================================================================================
The Loki bot pipeline has always died at ONE place:

    ULokiBotSpawnerComponent::SpawnBot 0x556D910
      -> MakeNewBotController 0x5563660
           0x55636BB  call 0x0F7EB50     STRIPPED -> nullptr      <== FK-22's getter
           0x55636C8  je   -> EXIT       controller NULL
      -> 0x556DD34 test rcx,rcx / je     Possess SKIPPED
      -> no PlayerState -> ServerSetHeroClass / SetPlayerTeam never reached

[M] SpawnBot takes an `AController* PremadeBotController`, and a NON-NULL value short-circuits
**before** MakeNewBotController is ever called:

    0x556DA4F  48 8b 44 24 70        mov rax,[rsp+0x70]        the parameter
    0x556DAA1  48 85 c0              test rax,rax
    0x556DAA4  0f 85 88 00 00 00     jne 0x556DB32             skips 0x556DAAA..0x556DB30

and the skipped region's ONLY memory writes are three stores to SpawnBot's own stack frame.
=> **the stripped getter is never reached.** The Blueprint route cannot do this
(`Comp_BP_BotSpawner_C::SpawnClassBotAtLoc` hardcodes `EX_NoObject` in that slot) -- but S137 can now
MANUFACTURE the argument: ARM D produces an `ALokiBotController` possessing a hero, and ARM B gives
it a real `BP_LokiPlayerState_C` at `+0x3C0`, which is the exact field SpawnBot consumes.

1. THE CALL
================================================================================================
The RAW IMPL at `0x556D910`, not the exec thunk. 7 native args:

  void* __fastcall(void* comp, UClass** heroClassCell, double locXYZ[3], int32 teamIndex,
                   uint8 difficulty, void* premadeController, void* botNameFString)
  rcx / rdx / r8 / r9d, then [rsp+0x20] difficulty, [rsp+0x28] premade, [rsp+0x30] &botName.

It RETURNS the spawned `ALokiHeroCharacter*` directly, so the `CreatedBot` out-param trap (a
`GetPlayerStatesOnTeam` scan that can return a PRE-EXISTING bot, or nothing, at that instant) does
NOT apply to a direct call. **The census delta is still the verdict; the return is a corroborator.**

⚠⚠ `BotName` is a ZEROED 16-byte FString. SpawnBot fills it and FREES it with the GAME's
`FMemory::Free` (`0xFF9310`) on BOTH exit paths, so a shim-CRT buffer there is heap corruption.

⚠⚠ RISK CLASS: **NOT CALL-ONLY.** A lane graded it CALL-ONLY and its own adversarial refuter
REFUTED that -- an exhaustive operand scan finds **7 non-stack writes across FOUR objects**.
SEH-guarded and separately knob-gated. This is a DIAGNOSIS, not a shipping fix.

⚠ It RE-POSSESSES. ARM D's controller is already possessing a pawn, so SpawnBot's `Possess` will
unpossess it first, driving `ALokiBotController::OnUnPossess` (`0x55667F0`) -- DARK in every image on
disk, never executed anywhere, ever. That is a real hazard AND a free receipt (§3).

================================================================================================
G1  `AController::Possess`'s authority test on our premade controller. VERIFIED BYTES:
        0x36E2B86  test byte [rcx+0x448],4  / 0x36E2B93 jne 0x36E2E13   -> PROCEED
        0x36E2B99  cmp  byte [rcx+0x160],3  / 0x36E2BA0 je  0x36E2E13   -> PROCEED
        fallthrough 0x36E2BA6 = the FMessageLog warning; 0x36E2E13 reads Pawn+0x3F8 and calls
        [rax+0x868] = slot 269 = OnPossess.
    ⚠ A lane described `0x36E2BA0` as where Possess "refuses". **It is the jump to SUCCESS.**
    ★ Already [M]-passed BY CONSEQUENCE (ARM D's controller reached OnPossess), but read anyway:
      "we think it passed" is not "we watched it pass".
G2  `PlayerState->PlatformPlayerID` ArrayNum: `0x556DD89 cmp dword [rdi+0x8c8],1 / jg 0x556DE58`.
    If > 1 the jg SKIPS bot-naming + ServerSetHeroClass + SetPlayerTeam -- the interesting half --
    while SpawnBot STILL returns a pawn. A null there would look like failure and would not be.

G3/G4  a live `ALokiGameState` and its `TeamStates` (`+0x600`). Informational, not blocking:
    SpawnBot calls its OWN `GetLokiGameState` (`0x56F01A0`) and `GetTeamState` (`0x5696D60`), and an
    empty team array makes those gates fail -- suppressing the §3 receipt -- while SpawnBot still

G6  a 16-byte PROLOGUE SIGNATURE on `0x556D910`
    (`40 55 53 56 57 41 54 41 55 41 56 41 57 48 8d ac`, transcribed offline and re-read by hand).
    It is a raw impl with no vtable slot to validate against, so this is the only self-validation
    available -- the same substitute ARM C uses.

4. WHAT WOULD MAKE THE RESULT UNINTERPRETABLE
================================================================================================
U1  ARM E REFUSED at a gate -> a STAGING statement. The census delta is UNINTERPRETABLE for ARM E.
U2  A non-null return with `0x5556D50` STILL DARK -> execution did NOT pass the PlayerState gate;
    the interesting half did not run, whatever the return value says. **Check the page before
    claiming the wall is broken.**
U3  G2 reported > 1, or TeamStates empty -> a null is explained by that, not by the wall.
U4  `[BS] done` absent, or `called=0` -> the arm was a no-op (the S136 lesson). A census delta with
    `called=0` is UNINTERPRETABLE, not a null.
U5  The client dies before the capture. Both S137 sittings ended in FK-32; **capture as you go.**

⛔ EVEN ON FULL SUCCESS THIS IS NOT A COMPLETE BOT. `ServerSetHeroClass` (`0x556DE43 -> 0xF7EC20`)
and `SetPlayerTeam` (`0x556DE53 -> 0xF7EB60`) are stripped folds and remain so. A pawn is not a
configured bot. Say "SpawnBot ran its premade path" -- never "the bot spawner works".
