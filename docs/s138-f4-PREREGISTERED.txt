================================================================================================

v3 adds a per-pass reset AND dedupe-on-insert. Therefore:

  D1  "G3/G4 GameState candidates: 1"                     (exactly 1, not 2)
  D2  exactly ONE gsCand line, class BP_LokiGameState_Tutorial_C, chain containing an element
      exactly "LokiGameState"

  D4  LokiGameStateUAVComponent STILL absent (the v2 latch fix must not regress)
  D5  TeamStates Data=0x0 Num=0 on that candidate (matches v2 and the offline result)

  ⚠ D1 is the discriminating one. If it still reads 2 with two DISTINCT pointers, that is a REAL
    ambiguity and a new finding, not a defect. If it reads 2 with the SAME pointer, the dedupe
    failed and v3 is broken -- the standalone logic test (10/10) would then be contradicted by the
    live build, which would itself be worth knowing.

  L1  Read LivingState on a BOT pawn (the one ARM E/ARM D produced).
  L2  Read LivingState on the PLAYER hero in the SAME pass -- the POSITIVE CONTROL. The player hero
      is possessed and alive, so if the probe cannot show a sane value THERE, any bot reading is
      UNINTERPRETABLE rather than a null.
  L3  Predicted: the bot pawn's LivingState is NOT the "Alive" value the player hero shows.
      If they are EQUAL, then LivingState is not the failing term and the gate fails on IsStunned
      or on something else -- which would be an equally useful result and must be reported as such.

  ⚠ This is OPPORTUNISTIC. It rides along on a client staged for the primary prediction. If the
    client dies first, L1-L3 are simply not obtained -- that is not a negative result about
    LivingState, and it must not be written up as one.
  ⚠ The offset is NOT recorded anywhere. It must be resolved BY NAME off the live class, and if it
    does not resolve by name the probe must say NOT RESOLVED rather than read a guessed offset.
