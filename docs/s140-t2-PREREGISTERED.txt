0. THE QUESTION, AND WHY THE OBVIOUS EXPERIMENT DOES NOT ANSWER IT
=================================================================================================
S139 recorded [M] "ULokiCMC::StartNewPhysics has NEVER run on either component", from CMC+0x16C8
reading 0.  S140 Tier 1 RETRACTED that: +0x16C8 is not a sticky latch, it is a per-frame
TOptional<FVector> validity flag -- SET inside StartNewPhysics at 0x055C2469 and CLEARED later in
the SAME engine PerformMovement call by ULokiCMC vtable disp 0xA50 (0x0530ABF0), on a path the
StartNewPhysics call site DOMINATES.  An off-thread reader observes 0 whether the step runs every
frame or never runs at all.  The instrument was invalid; the question is still open.

The DURABLE receipt is the PAYLOAD, not the flag:

    0x055C2448  movups xmm0,[rcx+0xe8]        ; Velocity (3 doubles, UE5 LWC)
    0x055C244F  movups [rcx+0x16b0], xmm0     ; snapshot X,Y   <-- the ONLY CMC-side payload writer
    0x055C2456  movsd  xmm1,[rcx+0xf8]
    0x055C245E  movsd  [rcx+0x16c0], xmm1     ; snapshot Z
    0x055C2469  mov byte [rcx+0x16c8], 1      ; the flag
    0x055C2470  jmp 0x3600990                 ; tail -> engine StartNewPhysics

disp 0xA50 clears ONLY the flag byte; it never touches the payload.

*** BUT THE HANDOFF'S SENTINEL-ONLY DESIGN IS DEGENERATE, AND TIER 1 SS7 SAYS SO. ***
With Velocity resting at (0,0,0) and NewObject zero-filling the object, "snapshotted a zero
Velocity" and "never written at all" are THE SAME BYTES.  S139 already banked
    docs/s139-f1-BOT.txt:19       R1.velsnap@0x16B0 | (0.000,0.000,0.000)
    docs/s139-f1-BASELINE.txt:20  R1.velsnap@0x16B0 | None | (0.000,0.000,0.000)
and it means NOTHING.  It is not a second independent negative and must never be cited as one.

=> THIS ARM PRE-POISONS THE PAYLOAD FIRST.  A distinctive value written into +0x16B0..+0x16C7
makes never-written and written-with-zeros DIFFERENT BYTES -- and it does so WITHOUT touching
Velocity at all.

THE POISON IS PROVABLY UNREACHABLE BY ANY CONSUMER.  The payload's only reader is
GetRecentVelocity (.data 0x09BC9AD0 -> impl 0x0530AC10; same cmove idiom at 0x0530C7FF and
0x0559C59E):  cmp byte [rcx+0x16c8],0 / mov eax,0x16b0 / mov r8d,0xe8 / cmove eax,r8d
-- it returns the PAYLOAD only when the flag is NON-ZERO, and the only writer of flag=1 writes the
payload 0x1A bytes earlier in the same straight-line block.  So while the flag is 0 the poison
cannot be read, and the instant the flag becomes 1 the poison is already gone.  The arm READS THE
FLAG FIRST and REFUSES to poison if it is non-zero.

1. THE ARM -- exactly what it does, in order
=================================================================================================
Game thread (BsPsSentinel(), end of BsPsExperiment, inside the one-shot BsLadderStep):
  1. print this outcome table into the marker BEFORE any write
  2. resolve BOT CMC:    g_psLbCtl[1] -> +0x3F8 (pawn) -> CharacterMovement UPROPERTY BY NAME
     resolve PLAYER CMC: g_bsPlayerHero            -> CharacterMovement UPROPERTY BY NAME
     (+0x458 is printed as a cross-check only, NEVER used as a fallback: an unvalidated offset
      that "agrees" is not corroboration when both can read zero -- the S138 +0xE0/+0xE8 lesson)
  3. IDENTITY CONTROLS, both mandatory, REFUSE on failure:
       CONTROL1  CMC+0x198 (CharacterOwner) == pawn
       CONTROL2  CMC+0x68  (FTickFunction::Target) == cmc
     ALokiCharacter has its OWN live bytes at +0x16B0/+0x16C8, so a probe aimed at the PAWN
     decodes a plausible WRONG value.  A failure here is an INSTRUMENT statement, not a result.
  4. THE THREE FREE READS (Tier 1 SS7 ranks 2/3/4, never taken live by anyone):
       CMC+0xC0  WorldPrivate            -- engine PerformMovement exit 2's input
       CMC+0x3E4 MaxSimulationIterations -- a FOURTH engine-StartNewPhysics early-out at 0x036009B5
       *(uint64*)CMC vs base+0x088F8570  -- is this really a ULokiCMC?
       (+0x3DC NumJumpApexAttempts and +0x3E0 MaxSimulationTimeStep ride along free)
  5. raw hex dump of +0x16B0..+0x16C7 and +0xE8..+0xFF, BEFORE
  6. read flag +0x16C8 on each; poison ONLY if it reads 0
       BOT poison    = (-9876.5,  -8765.25,  -7654.125)
       PLAYER poison = (-1234.5,  -2345.25,  -3456.125)     <- DIFFERENT ON PURPOSE
  7. BOT ONLY: Velocity CMC+0xE8/F0/F8 = (0.0009765625, 0, 0) = 2^-10, exactly representable,
     ~0.001 uu/s and therefore physically inert.  The PLAYER's Velocity is NOT TOUCHED.
  8. raw hex dump AFTER; every write readback-verified.

Worker thread (ShSampleLoop(), in the RM_BOTSPAWN branch, AFTER FsDisarm()):
  samples at t = +250 / +750 / +2000 / +5000 / +10000 ms, each printing raw hex + decoded doubles
  + flag + TimeSinceFallingStart(+0x12B0) + Acceleration(+0x328) + pawn location, then a VERDICT
  computed from the OBSERVED bytes.  Finally: BOT Velocity restored to (0,0,0), readback-verified.

*** WHY THE READ IS ON THE WORKER THREAD AND NOT IN THE ARM.  BsLadderStep runs ON THE GAME THREAD
inside OnPI, so every Sleep() in it BLOCKS THE GAME THREAD AND NO FRAMES PASS.  A
write-Sleep-read inside BsPsSentinel would be GUARANTEED to read the un-updated payload, and the
result would have been written up as "StartNewPhysics does not run" -- a false negative
manufactured entirely by the instrument.  The sampler therefore runs after FsDisarm, where the
game thread is free (the RM_DROPPLANE B4 precedent).  This is the single most important design
decision in the arm and it is why the handoff's one-line recipe would not have worked. ***

 - vptr is not the ULokiCMC vtable                        -> the whole test is void
 - TimeSinceFallingStart does not advance (P-D)           -> "the poison survived" is meaningless
 - the client dies before the sampler completes           -> NOT OBTAINED; do not reinterpret
