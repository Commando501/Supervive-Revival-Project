What the metadata-only census answers with just AB_OFF pinned
------------------------------------------------------------
With AB_OFF=0xd0 pinned but STRIDE/NAMEOFF unpinned, the census reads:
  [BIND][initial-pc]   ic=<addr> AB@0xd0 data=<addr> num=N max=M
  [BIND][initial-pawn] ic=<addr> AB@0xd0 data=<addr> num=N max=M
This is enough to distinguish:
  * PAWN has bindings (Num > 0)  vs  PAWN has none (Num == 0)
  * PC   has bindings (Num > 0)  vs  PC   has none (Num == 0)
The H2a case ("BP never wired") is decided by "PAWN Num > 0 AND PC Num == 0".
The H2b case ("ASC consumed first") requires the per-entry `bConsumeInput`
byte, which needs STRIDE + NAMEOFF pinned live. If Move 3's metadata reads
land inconclusive between H2a and H2b, one live-process RPM pass suffices
to derive STRIDE / NAMEOFF for a follow-up flight -- see "Case A" below.

Per-hit sample fields (what the marker file will contain)
---------------------------------------------------------
Pre-existing [S147][*] lines still emit. New lines added by KBFBINDCENSUS:

  [BIND] resolved pc=0x<addr> pawn=0x<addr> (BP_HERO_*)
    -- one-time at worker-ready; if pc=NULL AND pawn=NULL the whole census is void.
    -- if ONLY one is null, the OTHER's census still runs (asymmetric answers are useful).

  [BIND][initial-pc]   ic=0x<addr> AB@0xd0 data=0x<addr> num=N max=M
  [BIND][initial-pawn] ic=0x<addr> AB@0xd0 data=0x<addr> num=N max=M
    -- baseline InputComponent state on PC and pawn BEFORE any input arrives.
    -- ic=NULL means that actor has no InputComponent bound; the census skips it.
    -- num=N max=M is the DECISIVE data for the H2a discriminator.

  [FS][HB] tag=worker-ready phase=0 qpc=... ageMs=... calls=... swapped=...
    -- one-time when the sampling loop enters.
  [FS][HB] tag=worker-tick phase=0 qpc=... ageMs=... calls=... swapped=...
    -- periodic (KBFBINDCENSUS_HBMS=500 ms) throughout the sampling window.
  [FS][HB] tag=FsDisarm-enter phase=1 ...       -- FsDisarm just started.
  [FS][HB] tag=FsDisarm-done phase=2 ...        -- FsDisarm completed cleanly.
  [FS][HB] tag=FsDisarm-fault phase=3 ...       -- FsDisarm SEH-caught (only
                                                    reachable via BfS149FsDisarmGuarded,
                                                    which does not wrap FsDisarm
                                                    under KBFNATURALINPUT; so this
                                                    line is NOT expected on this arm).

  [BIND][sample-pc]   ...
  [BIND][sample-pawn] ...
    -- ActionBindings censuses re-run on each sample-log transition. Catches
       bindings that get installed dynamically in response to key presses (e.g.
       a delegate that binds on first activation).

Pre-registered outcome mapping (decisive on H2a; ambiguous H2b vs H1 without STRIDE)
-----------------------------------------------------------------------------------
The decisive PAWN vs PC comparison uses the Num field from AB@0xd0+0x8. All four
cases below key off (PAWN Num, PC Num) at the "initial" (pre-input) and "sample"
(post-input) censuses.

CASE A -- INSTRUMENT VOID.
  [BIND] resolved pc=NULL AND pawn=NULL, OR every subsequent census returns
  ic=NULL / shape-fail / SEH.
  ==> Do NOT interpret any counts. Retry with a different lookup strategy
      (e.g. resolve pc via GameInstance->LocalPlayers, or pawn via
      pc->AcknowledgedPawn); OR the AB_OFF pin is wrong (unlikely -- direct
      byte read from the ctor).

CASE H2a -- BP NEVER WIRED. [DECISIVE with just AB_OFF]
  PAWN Num >= 1 (initial or sample) AND PC Num == 0 throughout.
  ==> The BP K2Node `InpActEvt_Ability3_K2Node_InputActionEvent` is not
      installed on the PC's InputComponent. The ASC delegate on the pawn is
      the only Ability3 consumer -- input never reaches BP by design in
      this build. S147's "BP hit count 0" is trivially explained; not a
      coverage gap. WALL P residual is not an input problem.

CASE BOTH-WIRED -- H2b OR H1. [AMBIGUOUS without per-entry walk]
  Both PAWN Num >= 1 AND PC Num >= 1.
  ==> Both consumers exist. Whether ASC consumed first (H2b) or downstream
      code killed after both saw input (H1) requires reading the pawn-side
      Ability3 binding's `bConsumeInput` byte -- STRIDE + NAMEOFF must be
      pinned. FOLLOW-UP: derive STRIDE via live scan (walk PAWN's ActionBindings
      data with candidate strides {0x50,0x58,0x60,0x68,0x70}; the stride that
      produces `Num` valid FName ComparisonIndex values is correct); then
      rebuild with -DKBFBINDCENSUS_STRIDE=0x?? -DKBFBINDCENSUS_NAMEOFF=0x??
      and re-fly.

CASE NEITHER-WIRED.
  PAWN Num == 0 AND PC Num == 0.
  ==> The InputComponent has no ActionBindings at all -- the game hasn't
      wired input yet, or we're reading it at the wrong lifecycle moment.
      Instrument-void; re-derive lookup strategy or timing.

CASE H1 CORROBORATION (independent of PAWN/PC counts).
  Regardless of the counts above: if
  [FS][HB] tag=FsDisarm-done phase=2 line appears BEFORE the process dies
  AND flight 5's activation state moves fire (ActiveCount 0->1, Mana 10->0)
  ==> Input reached the ASC, activation body executed, disarm completed
      cleanly, protector integrity sweep killed the process AFTER. WALL P
      residual is the downstream activation body on the DARK page 0x4480000
      area. Corroborates H1 whichever H2 outcome above holds.

CASE FUNCSWAP-DISARM-KILL.
  [FS][HB] tag=FsDisarm-enter phase=1 appears but no `-done phase=2`; process
  dies with the last observed heartbeat still showing RUNNING.
  ==> The funcswap disarm itself is the trigger. This is NOT H1 causally
      -- fixing disarm would eliminate the 0xDEAD without addressing WALL P
      root cause.
