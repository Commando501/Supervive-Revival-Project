Move 4 verifier tool
--------------------
Path: tools/re/move4_bind_verify.py (this session, new).
Read-only RPM. Enumerates every live AbilitySystemComponent-shaped UObject,
resolves the AvatarActor property offset BY NAME per class (never
hardcoded), and:
  * Reports PASS (exit 0) when some ASC has AvatarActor==<hero> AND
    SpawnedAttributes.Num >= 1.
  * FAIL_BIND_LOST (exit 3) when no ASC has AvatarActor==<hero>.
  * FAIL_NO_ATTRSET (exit 4) when bind is live but SpawnedAttributes is empty
    (skips S148 injection -- preserves the FK-32 draw for a targeted follow-up).
  * FAIL_NO_ASC (exit 5) when no ASC objects exist at all.
The flight helper branches on exit code.

Pre-registered outcome mapping
------------------------------

CASE H (headline) -- MOVE 4 SUCCESS.
  [S148] RESULT=HEALTH_APPLIED ... (or equivalent success shape from
  the S148 arm's own vocabulary)
  Helper exits 0.
  ==> First live AdjustHealth receipt on the force-open route. WALL E
      Phase 1a proved: the damage pipeline runs client-side with no
      server authority. Independent of any WALL P activation work.

CASE R -- S148 armed and refused.
  [S148] RESULT=PREFLIGHT_REFUSED issues=0x<mask> ...
  Helper exits 2.
  ==> Bind was live enough to pass the verifier but S148 still refused.
      Read the issue bitmask. If it does NOT include bit 17
      (AVATAR_BINDING), the bind persisted; the refusal is a DIFFERENT
      precondition we haven't accounted for. If it DOES include bit 17,
      the bind died between the verifier and S148 injection (~20 s
      window) -- diagnose GC or hero re-possession as candidates.

CASE B -- bind lost between S149 and verifier.
  Helper exits 3 (verifier FAIL_BIND_LOST).
  ==> S149 bind-only produced a receipt, but by the time the verifier
      read the ASC set, no ASC had AvatarActor==<hero>. S148 was NOT
      injected (draw preserved). Two possibilities:
        (i) the bind was written to a DIFFERENT ASC than the one the
            verifier looked at -- multiple ASCs may coexist, and S143's
            persistence claim was on the exact ASC S149 chose.
        (ii) GC or a game-side re-init cleared the bind between the two
             reads.
      Diagnose by re-running with a wider verifier (list all ASCs +
      AvatarActor values, not just matches).

CASE A -- bind live but no attribute sets.
  Helper exits 4 (verifier FAIL_NO_ATTRSET).
  ==> The load-bearing open item from the design. AvatarActor is bound
      but the ASC's SpawnedAttributes is empty, so S148 would refuse on
      HEALTH_COUNT. S148 was NOT injected. Design implication: bind
      alone is insufficient; a preceding step must populate the
      attribute set. That's a real WALL E finding -- the next flight
      would design an attribute-set-populating step (possibly via
      WireAbilitySystem's TryUpdateAbilitySystem path, tutorial_launch.cpp
      :20053 in the codex source).

CASE V -- verifier itself failed to run.
  Helper exits 5, 6, or 9 (FAIL_NO_ASC / FAIL_HERO_MALFORMED / FAIL_INSTRUMENT).
  ==> Instrument fault. Diagnose the verifier's stdout in
      docs/s148-move4-flight1-<UTC>/move4_bind_verify-*.out.txt.

CASE S -- no bind receipt.
  Helper exits 22 (bind-only marker never emitted PLAYER-POST-BIND).
  ==> Either bind-only DLL failed to inject (unlikely; sha256 pinned) or
      the ReportAscActorInfo path was gated out. Read the marker's
      after-bind snapshot in the evidence dir.

CASE F -- FK-32 kill.
  Process dies mid-sequence with no RESULT and no crashpad.
  ==> Historical hazard. Move 4 is 5 injections vs the modal FK-32
      count of 4 (per S141 series). ZERO precedent for a 5-injection
      sequence surviving to RESULT. The exit-4 short-circuit saves the
      draw when SpawnedAttributes is empty, so an actual 5-injection
      run only happens on the design's success case.

Load-bearing risk (from the workflow's design report)
-----------------------------------------------------
"S149 bind-only leaves SpawnedAttributes empty" -- if this is TRUE,
Move 4 always lands in CASE A (helper exit 4), producing an
INFORMATIVE partial result but not the AdjustHealth receipt. The
verifier design pre-empts this by skipping the S148 injection when
SpawnedAttributes is empty -- so the FK-32 draw is preserved for a
targeted follow-up rather than spent producing an already-predicted
refusal.

Mitigation IF CASE A lands: the next arm would need to run
`WireAbilitySystem` (tutorial_launch.cpp:20053 in codex source) as
part of the bind-only DLL's flow, or add a separate attribute-set-
populating step between bind and S148. That's a next-session
implementation, not a flight.
