WHAT SESSION 42 LEFT: the scan (ScanPathsForPrimaryAssets) populates the AssetManager
per-type AssetMaps (Hero 0->25), but a POST-menu scan is too late — the menu builds its
hero catalog ONCE at menu-load (ChangeBundleStateForPrimaryAssets) and caches it, so the
grid stays empty. Early-injecting scan_shim to scan pre-menu CRASHED (its worker
brute-force-scanned ALL private memory repeatedly during volatile early-init -> AV).

THE S43 FIX (design): hook UEngine::Browse (RVA +0x3EC57D0) with browse_hook's proven
early-injection machinery, and when the LobbyV2 map is browsed, run the asset scan on the
game thread BEFORE continuing the original Browse. This runs the scan at the exact right
moment WITHOUT scan_shim's fatal flaw: the hook is installed PASSIVELY early (only reads a
fixed RVA), and the manager-find + asset-scan run LATER, at LobbyV2-Browse time, when the
process is fully stable (same stability as the proven post-menu scan). Deterministic
timing — no APC gamble.

TIMING WINDOW (verified from a normal-client Loki.log, all on the game thread [frame]):
   :Login  Browse LVL_Login
   ...     (login screen up ~8-18s)
   :LB     Browse LVL_LobbyV2_Persistent   <-- HOOK FIRES; scan runs here
   :LB+~1  LoadMap LobbyV2 complete
   :LB+~1.5 ChangeBundleStateForPrimaryAssets failed to find NameData  <-- catalog build
So the scan at the LobbyV2 Browse runs ~1.5s BEFORE the catalog build. CONFIRMED by a
~10s game-thread FREEZE gap in the log immediately before the "Started Browse LobbyV2"
line (the manager-find blocking the game thread) — i.e. the scan provably completes
before the catalog build.

RESULTS (live, non-elevated gated `inject watch` on the Browse prologue):
1. EARLY INJECTION IS STABLE. scan_on_browse injects, installs the Browse hook, and the
   game reaches the login screen and menu with NO early-init crash. scan_shim's
   early-injection crash is ELIMINATED (no worker memory-scan during unpack).
2. HOOK FIRES AT THE RIGHT TIME. "[pre] LobbyV2 Browse detected" -> scan runs on the game
   thread -> "scan complete; continuing original Browse", before the catalog build.
3. MANAGER-FIND BUG FOUND + FIXED. First live run picked a BOGUS instance (typemap num=1,
   data=0x7FF600000000 non-heap) because the old heuristic took the FIRST vtable hit with
   num>0. Fix: pick the MAX-num instance (only the real singleton has ~30 types), validate
   the typemap data is a readable heap pointer, early-out at num>=25. After the fix it
   reliably finds the real singleton (num=30) and populates: Hero added=25, all 30 types,
   counts matching the S42 post-menu run (Item=510, Emote=331, cues 961/2296, ...).
4. THE FIX WORKS at the enumeration layer: the scan runs before the catalog build and
   populates Hero's AssetMap to 25 — exactly what S42 said the empty grid needed.

*** BUT POPULATING THE GRID CRASHES THE GAME ***
The game reaches the full main menu (BP_MainMenuGameMode_C, TryUIReady SUCCESS) and then
crashes via Sentry (no UECC dump; Sentry intercepts). Single-variable tests
(same inject/hook/manager-find, only the populate toggled), monitored for liveness:

   VARIANT (POPULATE)          assets registered            crash time after menu
   ---------------------------  ---------------------------  --------------------------
   full (all 30 types)          Hero=25 + ~7000 others       ~9-50s  (2 runs)
   hero-only (Hero type)        Hero=25 only                 ~2.5 min (1 run)
   control (no populate)        none (find only)             ~4.75 min (1 run)  <-- CRASHED
   unmodded normal client (S42) none                         stable for HOURS

*** THE CONFOUND: EVEN THE NO-POPULATE CONTROL CRASHES (~4.75 min). ***
This overturns the initial "populate hits the rendering wall" read. All three variants
share a ~10s GAME-THREAD FREEZE (the brute-force full-address-space manager-find inside
the Browse hook, blocking the game thread during LoadMap). The no-populate control does
NOTHING but inject + hook + that freeze, yet it still crashes at ~4.75 min — while the
unmodded client runs for hours. So the FREEZE (or the injection/hook) is a BASE
DESTABILIZER, and the populate merely ACCELERATES the crash (more assets -> faster). The
crash CANNOT be cleanly attributed to the populate/rendering while this freeze exists.

FREEZE ELIMINATED (session 43): the manager is now found via GEngine->AssetManager —
rcx in UEngine::Browse IS GEngine (UEngine*), and UEngine holds the UAssetManager* at
**offset 0x340** (this build). Scanning only UEngine's own memory (a few KB) finds it
INSTANTLY — no full-address-space walk, no game-thread freeze. VERIFIED live:
"[find] via GEngine+0x340 -> manager=... typemap num=30", Hero added=25, and NO 10s
timestamp gap before the LobbyV2 Browse in Loki.log. (Full-address-space ScanForManager
kept as a fallback.)

*** VERDICT: FIX COMPLETE — grids populated AND the game is stable. ***
The base destabilizer was the PERSISTENT UEngine::Browse PATCH (a periodic code-integrity
check crashes the game ~3-5 min after detecting the modified prologue). Two changes fixed it:

  (1) FREEZE-FREE FIND via GEngine->AssetManager (offset 0x340) — removed the ~10s
      game-thread freeze. Alone this only DELAYED the crash (full-populate 50s -> 204s).
  (2) UN-HOOK after the scan — restore the original Browse prologue ~1.5s after the
      one-shot scan (worker thread; safe, no Browse in flight at idle menu). The hook is
      only needed to trigger the scan; reverting it leaves Browse pristine for the
      integrity check.
