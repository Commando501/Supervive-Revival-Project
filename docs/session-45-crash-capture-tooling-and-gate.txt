=========================== THE DISCRIMINATOR (evidence, not yet proof) =======
Is the hero-content-load crash the SAME D3D12/RHI wall as S40/41, or something else
(a throttleable streaming/asset/GC failure)? Two honest signals:
  (1) UECC-dump asymmetry: S40/41's D3D12 RHI-thread AVs RELIABLY produced UECC
      minidumps (UE's structured-exception handler -> CrashReportClient -> UEMinidump.dmp,
      13-14 MB each, one per crash). The hero-content-load crash produces NONE, only
      Sentry crashpad. If it were the identical RHI-thread AV, the same UE handler should
      fire and write a UECC dump. Its absence LEANS AGAINST "identical to S40/41" (it
      could be a UE Fatal/check() during content processing, or a handler-race
      difference — unconfirmed).
  (2) Log fingerprint is a WORLD TEARDOWN: hero GameplayCue load -> LogSlate
      InvalidateAllWidgets -> LogAudio "Audio Device unregistered from world 'None'" ->
      LogUObjectHash "Compacting FUObjectHashTables" -> Sentry. That is UE destroying the
      current world, consistent with a fatal DURING content load, not specifically the
      D3D12 command-list/residency AV that S40/41 pinned (FRDGBuilder::Execute /
      FD3D12CommandList::Close, SUPERVIVE +0x296xxxx band, D3D12Core interleave).
NEITHER is conclusive. The faulting RIP is the only decisive discriminator. If it lands
in the SUPERVIVE +0x29xxxxx band or inside D3D12Core.dll -> same wall (render, likely
unsolvable client-side; anti-cheat walls the renderer CVars). If it's elsewhere (asset
streaming / GC / OOM) -> Path 2 (throttle/stage the load) is live and worth pursuing.
The evidence hint in (1) is a reason to GET the RIP, not to assume it's a dead end.

=========================== GRID WIDGET INSTRUMENTATION — THE FILTER, READ FROM CODE ===
Built tools/sigbypass-mod/trace_caller.cpp (+.dll) = trace_hooks + a stub that captures the

(docs/trace-caller-marker.txt): GetPrimaryAssetIdList(Hero) has TWO distinct call sites —
  caller RVA +0x562EBFE   and   caller RVA +0x3965BFC
and GetPrimaryAssetObject(Hero)=0, ChangeBundleState(Hero)=0. So the grid enumerates then drops
all 25 WITHOUT ever asking the AssetManager to resolve them. The drop is in the WIDGET.

Disassembled caller 1 (live RPM, usmapdump disasm). The GetPrimaryAssetIdList call is
`call [r10+0x370]` (slot 110) at +0x562EBF7. AFTER it returns, the populate loop (over the
returned TArray<FPrimaryAssetId> at rsi):
  for each id:
    lea rdx,[id]; mov rcx,r14; call +0x57AB3C0      ; PER-HERO LOOKUP into r14
    test rax,rax; jz SKIP                            ; <-- lookup null => DROP the hero
    (if r15b) cmp byte[rax+0xd2],0; jnz SKIP         ; secondary flag gate (display-mode)
    (if r12b) cmp byte[rax+0xd0],0; jz  SKIP         ; secondary flag gate (display-mode)
    ...add survivor to the tile array...
  (r12b/r15b derive from a byte arg 'dil' in {1,2} = a display/filter mode.)

The lookup fn +0x57AB3C0 (abs 0x7ff68822b3c0; decrypt it by running WITH the scan so the loop
executes it): hashes the FPrimaryAssetId (call +0x...d6a210), then does a TMap FIND into a map
at **r14+0x60** (call +0x...c99090 -> element index or -1; 32-byte entries; value @entry+0x10).
Found -> returns the per-hero value. index==-1 (NOT in the map) -> fallback path that tries to
NewObject from the id and returns null for our heroes -> hero dropped.

r14 = Singleton(+0x565E1C0)->[+0x1f0]->[+0x190]  (a NESTED member of a game singleton; NOT the
AssetManager, NOT the content manifest, NOT any server response). Its per-hero TMap @ r14+0x60
is keyed by hashed FPrimaryAssetId.

=========================== THE ACTUAL ROOT CAUSE (finally, from code) ========

side per-hero TMap at r14+0x60 (r14 = *(*(Singleton_565E1C0 +0x1f0) +0x190)). None of the 25

enumeration (a DIFFERENT structure), and the server populates the manifest/storefront (DIFFERENT
