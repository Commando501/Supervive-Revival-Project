    -> returns OutList directly. NO per-hero filter. (mode 0)

  Get Heroes Asset List Sorted  (47 statements)  [FUNC_BlueprintPure]

      ... else lowercase the hero display name, Map_Add(name -> id)

=========================== NATIVE GetHeroCharacterList — READ FROM CODE =======
GetHeroCharacterList is native (EX_CallMath). Its body = S45's "caller-1" function; disassembled the
LIVE decrypted code (usmapdump disasm). Function entry +0x562EB7B; args: rcx=WorldContext/this,
rdx=out TArray<FPrimaryAssetId>, r8b=AssetListKind (the byte "mode"):
   +0x562EB8D  movzx edi, r8b                 ; dil = AssetListKind
   +0x562EB97  mov [rdx+8], 0                 ; OutList.Num = 0  (clear)
   ... resolve this->[vtbl+0x188]() (slot 49) -> holder ; get AssetManager (+0x562EBCC) ...
   +0x562EBDA  cmp dil, 3 ; jnb return        ; AssetListKind >= 3 => bail (empty)
   +0x562EBEA  mov rdx, [Hero FName global]
   +0x562EBF7  call [r10+0x370]               ; GetPrimaryAssetIdList(AssetMgr, Hero, OutList, 0)
   +0x562EBFE  test dil, dil ; jz return      ; *** AssetListKind == 0  => RETURN ALL, NO FILTER ***
   +0x562EC26  sub ecx,1; jz .. ; cmp ecx,1;  ; AssetListKind 1 vs 2 dispatch -> the flag-gate loop
   (loop, per S45: CatalogManager(r14+0x60) lookup HITS; then drop by [entry+0xd2]!=0 (mode1) or
    [entry+0xd0]==0 (mode2))
=> AssetListKind 0 returns all 25 enumerated ids WITHOUT touching the CatalogManager or any flag.
   AssetListKind 1/2 apply the S45 CatalogManager flag filter. The enumeration itself (with the
   scan) yields 25, so GetHeroCharacterList is NOT where the heroes vanish for mode 0.

=========================== THE ACTUAL DROP (synthesis) =======================
The hunter UIs use the SORTED function. Its extra per-hero gate is:
   GetHeroAssetFromPrimaryAssetId(id) -> OutputExecs ; if OutputExecs == 0 -> DROP the hero.
GetHeroAssetFromPrimaryAssetId RESOLVES a hero PrimaryAssetId to its LokiHeroAsset object. This is
exactly the step S45 measured failing on the live client: GetPrimaryAssetObject(Hero)=0,
RequestAsyncLoad "null assets" x8, ChangeBundleState "failed to find NameData" x2. The CatalogManager
holding 25 CatalogEntry objects (S45) is NOT the same as the 25 LokiHeroAsset objects being loaded/
resolvable — the entries exist but the assets don't resolve, so GetHeroAssetFromPrimaryAssetId
returns the failure exec (OutputExecs==0) for every hero and the sorted list comes back EMPTY ->
empty grid, empty combobox, empty store carousel (all share BPFL_LokiAssets + the sorted path).

This RE-UNIFIES the two S45 diagnoses that seemed to conflict:
  - "heroes present + correctly keyed in CatalogManager"  (TRUE — the CatalogEntry map is full)
  - "client-side asset resolution fails"                  (TRUE — GetHeroAssetFromPrimaryAssetId /
     GetPrimaryAssetObject can't turn those ids into loaded LokiHeroAsset objects)
S45's very last reframe ("just a display flag; poke CatalogEntry+0xd0") was the incomplete part:
poking +0xd0 did nothing because (a) the sorted path never reaches the +0xd0/+0xd2 flag gate — it
drops heroes earlier, at GetHeroAssetFromPrimaryAssetId — and (b) +0xd0/+0xd2 only apply to
GetHeroCharacterList modes 1/2, which is upstream of the resolution gate anyway.

=========================== WHY THE DETAIL PANEL WORKS BUT THE GRID DOESN'T =====
S42's screenshot: the RIGHT detail panel showed a real hero ("Frontline Pyromaniac") by DIRECT id,
while the grid was empty. Consistent with the above: a single, directly-referenced hero can be
force-resolved/loaded (detail panel), but the bulk enumerate-then-resolve-each path
(GetHeroAssetFromPrimaryAssetId over all 25) fails to resolve them as primary assets, so the tile
list is empty. The blocker is bulk primary-asset RESOLUTION, not per-asset badness.
