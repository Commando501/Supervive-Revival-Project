=========================== THE ACTUAL DROP (synthesis) =======================
The hunter UIs use the SORTED function. Its extra per-hero gate is:
   GetHeroAssetFromPrimaryAssetId(id) -> OutputExecs ; KEEP iff OutputExecs == 0 (the success/valid
   exec pin), otherwise SKIP. The grid is empty => every enumerated hero returns a NON-zero (reject)
   exec, i.e. GetHeroAssetFromPrimaryAssetId is failing to resolve/validate all 25 ids.
GetHeroAssetFromPrimaryAssetId RESOLVES a hero PrimaryAssetId to its LokiHeroAsset object. This is
exactly the step S45 measured failing on the live client: GetPrimaryAssetObject(Hero)=0,
RequestAsyncLoad "null assets" x8, ChangeBundleState "failed to find NameData" x2. The CatalogManager
holding 25 CatalogEntry objects (S45) is NOT the same as the 25 LokiHeroAsset objects being loaded/
resolvable — the entries exist but the assets don't resolve, so GetHeroAssetFromPrimaryAssetId
returns the failure exec (OutputExecs==0) for every hero and the sorted list comes back EMPTY ->
empty grid, empty combobox, empty store carousel (all share BPFL_LokiAssets + the sorted path).

This RE-UNIFIES the two S45 diagnoses that seemed to conflict:
  - "heroes present + correctly keyed in CatalogManager"  (TRUE — the CatalogEntry map is full)
  - "client-side asset resolution fails"                  (TRUE — GetHeroAssetFromPrimaryAssetId /
     GetPrimaryAssetObject can't turn those ids into loaded LokiHeroAsset objects)
S45's very last reframe ("just a display flag; poke CatalogEntry+0xd0") was the incomplete part:
poking +0xd0 did nothing because (a) the sorted path never reaches the +0xd0/+0xd2 flag gate — it
drops heroes earlier, at GetHeroAssetFromPrimaryAssetId — and (b) +0xd0/+0xd2 only apply to
GetHeroCharacterList modes 1/2, which is upstream of the resolution gate anyway.

=========================== NATIVE GetHeroAssetFromPrimaryAssetId — READ FROM CODE (confirmed) ===
Located it in the live process: findptr on its FName id 0x005863F0 returned the native-function
table entry {FName 0x5863F0, execptr 0x7FF687D2A550 (RVA +0x52AA550)} AND the impl pointer
0x7FF6880AEA00 (RVA +0x562EA00) — the impl sits IMMEDIATELY BEFORE GetHeroCharacterList (+0x562EB7B),
a sibling in LokiAssetBlueprintLibrary. Disassembled the impl (entry +0x562E9F6; args rcx=out
ReturnValue FPrimaryAssetId, rdx=in FPrimaryAssetId id, r8=out byte OutputExecs):
   +0x562E9F6  push r13 ; sub rsp,0x30 ; movups [rcx+0x20],xmm0   ; zero the out ReturnValue
   +0x562EA11  mov byte [r8], 0x1                                  ; *** OutputExecs = 1 (REJECT) by default
   +0x562EA18  cmp [id.Type], [rip global] ; jz .. else reject     ; only Hero-type ids proceed
   ... resolve id -> object (TMap find + object fetch); at +0x562EB22 check obj flags
       ([obj+0xc]>>0x1e); ONLY on a valid resolved object:
   +0x562EB2E  mov byte [r15], 0                                   ; OutputExecs = 0 (KEEP)
   (failure path +0x562EB34 -> call +0x562EB49 = the "Invalid Primary Asset Type/Id" warning S45 saw)
=> CONFIRMED: OutputExecs defaults to 1 (reject); it becomes 0 (keep) ONLY when the hero id resolves
   to a valid loaded object. Heroes don't resolve (S45: GetPrimaryAssetObject=0, RequestAsyncLoad null)
   -> OutputExecs stays 1 -> the sorted BP loop drops all 25 -> empty grid. The whole chain (BP filter
   + native resolver) is now read end-to-end from code. THE FIX = make the 25 hero ids resolve to
   loaded objects (load the Hero bundle) so this returns OutputExecs==0.
