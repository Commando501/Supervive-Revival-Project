=========================== GOTCHAS LEARNED (this session) ===================
- FName ids DRIFT run-to-run despite the constant base — NEVER hardcode a name id; resolve LIVE
  (usmapdump nameid, or FindFName in-DLL). (ClientGlobal was 0x4CA778/0x4C9E51/0x4CBAC9/0x4CBAB0.)
- The packer decrypts each function's page ON FIRST EXECUTION. You CANNOT patch +0x562Exxx code at
  scan time (page still encrypted -> the byte isn't the expected opcode). Patch at MENU-LOAD inside
  h_idl_post on the Hero call — GetHeroCharacterList has run/decrypted the page by then, and it fires
  BEFORE the per-hero resolver calls. (catalog_probe does this.)
- JIT-capture/detour stubs MUST be NearAlloc'd within +-2GB of the patched call site (a `call rel32`
  can't reach a plain VirtualAlloc'd low address ~29GB away — it wraps -> crash). This caused 3 false
  "crashes" before the fix. Mirror probe_r14's "near-allocated" stub.
- open_application("Supervive-win64-shipping") LAUNCHES A NEW BARE instance (no -ini redirects, no scan)
  instead of focusing the running one — muddies verification. To focus the REAL scanned client, use
  PowerShell SetForegroundWindow on (Get-Process -Id <pid>).MainWindowHandle. Tell instances apart by
  cmdline: the real recon client has -ini:...ProdPostAuthURL=http://localhost:8080 ; a bare launch has none.
- Computer-use: grant the process by name "supervive-win64-shipping.exe" (the Steam app-id grant does
  NOT match the direct-launched process; the game gets masked). Menu input is laggy — SetForegroundWindow
  first, click twice, wait. HUNTERS is at ~(291,224) on the main menu; back-arrow ~(279,131) on HUNTERS.
- There IS a separate intermittent menu-load crash (hero GameplayCue load -> InvalidateAllWidgets storm
  -> Sentry, no UECC dump). scan_and_load survived it 4x; a retry usually boots. Don't confuse it with a
  probe bug.
