WHY THE ? PERSISTS (diagnosed S47, from BP bytecode — do NOT re-derive):
  HeroPickerSelectable_CatalogEntryWithPreview (the roster tile) has two mutually-exclusive gates on the
  hero's CatalogEntry:
    IsUseable    (Selectable) = Entry.CanUse()                    -> TRUE when you OWN the hero
    IsPreviewable            = (NOT Entry.CanUse()) AND (NOT Entry.IsDisabled())  -> TRUE only when UNOWNED
  So: UNOWNED hero => previewable (center loads the hero model to entice a buy), not selectable. OWNED hero
  => selectable (pick/play it), NOT previewable. Our owned-inventory change flipped all 25 to CanUse=true,
  which CORRECTLY disabled the purchase-preview. The center for OWNED heroes is a DIFFERENT actor: the
  party-slot spawner BP_MainMenuSpawner_MainMenu_PartySlot_C_0..3 (slot 0 = you). With no selected hero it
  shows BP_LokiHeroSelectPreview_UnknownHero and logs `RequestAsyncLoad() called with empty or only null
  assets` (no hero ref). => the "?" == "no active/selected hunter", the SAME state behind the main-menu "?".

=========================== catalog_ready_fix.cpp — how the roster fix works ==
tools/sigbypass-mod/catalog_ready_fix.cpp (DLL gitignored — rebuild). On the game thread it:
  (1) hooks GetPrimaryAssetIdList slot 110 + runs the 30-type ScanPathsForPrimaryAssets on the first call
      (so Hero enumerates 25 — WITHOUT this GetHeroCharacterList returns 0);
  (2) NOPs the `jz` at +0x57BB722 (74 0C -> 90 90) so IsCatalogDataReady ignores the never-set 5th flag and
      returns TRUE once the 4 real catalog flags [+0x350..+0x353] are set -> the game broadcasts
      OnCatalogDataReady -> WBP_HeroPicker.LoadCharacters runs -> AllHunters builds -> TileView renders;
  (3) find-once the live CatalogManager (its +0x60 map Num>=50 == catalog loaded); ~6s later RESTORES the jz
      (durable: no persistent .text mod => the ~3-5min code-integrity check never fires; a SURVIVING run
      lasted 7m34s+ with the roster populated and jzRestored=1). Also read-only VEH crash logger.
  A pure DATA poke of [+0x354]=1 (no code patch) is the truly-clean fix BUT needs the live instance set BEFORE
  the readiness check, which required a continuous full-memory scan that aggravated the fragile menu-load and
  crashed early — so find-once + jz + restore is the STABLE approach. (Truly injection-free = backend: make
  ags complete whatever content-service data sets CatMgr+0x354 — an open, optional RE task.)
