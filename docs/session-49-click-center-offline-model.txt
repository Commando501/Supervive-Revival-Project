=========================== WHY ROUTE B (S49 first half) WAS INERT — now fully explained =============
Route B tried to force owned tiles "previewable" by Func-swapping IsPreviewable/IsPreviewSelection to
true. Given the chain above, that premise was SOUND (true IsPreviewSelection would route owned clicks to
the working PREVIEW branch). It was inert because:
  (a) The Func-swap mechanism was never verified to actually redirect (the S49 handoff flagged this) — the
      counter stayed 0 even where IsPreviewSelection MUST be called (Update Hero Selection stmt 31/33 calls
      it on every notified click). Offline bytecode PROVES IsPreviewSelection is on the click path, so a
      0-count means the instrumentation did not fire, not that the code path is dead.
  (b) CommonUI TileView pools entry widgets; IsPreviewable is computed at first build and the pooled entry
      is reused, so a late heap patch of the predicate is not re-evaluated on click/refilter.
CONCLUSION: leaf-predicate patching is the wrong lever. Do not re-grind it.

*** THE PARTY SURFACE HAS NO HERO-PICK REST ROUTE (usmapdump wstrings, live RPM, read-only) ***
  The full Theorycraft party route-template table (UTF-16 FStrings, clustered at heap ~0x26B88B4Cxxx) is:
    /party/                         /join?joinSecret=            /members/            /joinQueue
    /setIsOpen/                     /setFillTeam/                /refreshRanks        /refreshRankedEligibility
    /refreshLevel                   /refreshMastery              /refreshXPBoosts     /setTargetQueues
    /setExcludedRegions             /latencies                   /referral            /leaveQueue
    /startSoloMode?mode=  (+ appended query: &soloModeStartPosition=  &hero=)
    /owner    /reconcile    /setDiscordUserID/    /voiceToken    /custom/voiceToken
    /party/matchmaking/info    /party/matchmaking/customGameModes
    /sendInvite/   /declineRequest/   /requestInvite   /declineInvite   /custom?cu...
  There is NO /setHero, /pickHero, /setMyHeroAndCosmetics, or per-member hero-write verb. The selected
  hero is transmitted ONLY as a QUERY PARAM `&hero=<id>` appended to
    POST /party/parties/{partyId}/startSoloMode?mode=<mode>&soloModeStartPosition=<pos>&hero=<heroId>
  i.e. the hero is sent to the server when you START A MODE/QUEUE, never on the tile click itself.
  (Nearby model strings: field "InitialHero"; validation msgs "Disabled heroes list exceeds maximum
  length of %d", "Cannot modify disabled assets while game is in progress"; keys tooManyHeroesDisabled/
  tooManyItemsDisabled/tooManyPerksDisabled.)

*** THE NATIVE PICK IS LOCAL-ONLY, GATED ON A PER-MEMBER BOOL (disasm of impl +0x58467E0) ***
  TryPickMyHeroAndCosmetics(this=PartyManager, &HeroAssetId, ...):
    rcx = [this+0xF8]                    ; members container
    call +0x5840730                      ; members getter -> data @[rsp+0x40], count @[rsp+0x48]
    for each member m in [data..data+8*count):
        rax = m
        if  byte [m+0x40] == 0 : continue    ; <-- ONLY members with the +0x40 bool set are processed
        rdi = &m[+0x110]                      ; per-member string/array field
        ... build the hero id (from r15) into the member ...   ; sets local member state, NO HTTP call
  So the pick does NOT emit HTTP; it mutates LOCAL member state, and only members whose byte at struct
  offset +0x40 is non-zero are touched. member+0x110 is where the picked hero is written. member+0x40:
  PartyMemberModel (UClass:Object) starts UPROPERTYs at ~+0x30 (UObject header ends Outer@+0x28); by rough
  declared-order layout +0x40 aligns with DisplayName (FString), so `cmp byte [m+0x40],0` is likely a
  DisplayName.Data null/empty check, NOT a bool — the struct's only bools (bIsReady, bIsOwner,
  bIsRankedEligible) sit at much higher offsets. buildSoloParty DOES send displayName (from the JWT); if
  the JWT display name is empty for this player, the gate would skip our member. RESOLVE LIVE: findptr the
  local PartyMemberModel and `peek +0x40` / `peek +0x110` to read actual values rather than trusting
  offset math. PartyMemberModel prop order (usmap): ID, DisplayName, Tag, DiscordUserID, PlayerModel,
  HeroAssetID, CosmeticsAssetID, bIsReady, bIsOwner, ..., bIsRankedEligible (34 props total).

=========================== THE FIX — REVISED ranking (R1 backend-route is OUT) =====================

   captured hero-pick route in ags" is a DEAD END. The pick is a LOCAL native state mutation. Do not add
   speculative /setHero-style routes.

R1' (BACKEND-adjacent, low-risk, try FIRST) — make the LOCAL native pick actually run against our
   synthesized party by satisfying the member+0x40 gate. buildSoloParty currently sets id/userId/memberId/

   bool we are NOT populating (or populating with the wrong value), the pick's loop skips our member and
   never writes the hero -> center inert. ACTION: resolve member+0x40's field from the PartyMemberModel
   usmap layout, then set it in buildSoloParty. Harmless if wrong (UE ignores unmatched keys); if right,
   the pick runs locally on click and the center updates. STILL needs a live click to confirm the pick is
   even reached (see experiment).

R2 (native, force preview branch) — patch IsPreviewSelection to return TRUE so owned clicks take the
   working PREVIEW branch. Needs a VERIFIED heap patch mechanism (UFunction Func-swap or Script-bytecode

   Downside: the preview branch may present purchase/preview affordances meant for unowned heroes.

R3 (native, hijack the pick) — patch the OWNED branch / TryPick (or member+0x40 at runtime) so the local
   pick writes member.HeroAssetID, firing OnHeroAssetIDChanged. Most robust client-side guarantee of a

=========================== *** LIVE SESSION 2 (2026-07-04 eve, user drove clicks) — FUNC-SWAP IS DEAD *** ==
Ran the passthrough-Func-swap experiment on the live client (PID 62212, read-only+heap patches, restored
clean after). Located the tile-class UFunctions live (same process route-B used, objects still valid):
  IsPreviewable @0x26D001D6F00 (slot +0xE0 =0x26D001D6FE0), IsUseable @0x26D001D6E00 (0x26D001D6EE0),
  ShouldHideHero @0x26D001D6900 (0x26D001D69E0)  — Outer=HeroPickerSelectable_CatalogEntryWithPreview_C.
  Tools: tools/re/scan_ufunc_local.py (cluster-scan by FName id), tools/re/patch_passthrough.py
  (count + jmp ProcessInternal, so the fn still runs).
EXPERIMENT: patched ShouldHideHero (the MECHANISM CONTROL — it is called for every hero by UpdateFilteredList
on any role-filter change) across ALL 6 selectable variants (_CatalogEntryWithPreview_C, _CatalogEntry_C,
_CatalogEntryAll_C, _HeroUnlock_C, _WithCustomGameFilter_C, _C base). USER filtered repeatedly; the roster
VISIBLY narrowed by role (so UpdateFilteredList + ShouldHideHero DEFINITELY ran). RESULT: **every counter = 0.**
CONCLUSION: patching UFunction+0xE0 (Func) does NOT redirect these calls. STRUCTURAL REASON: for a BP->BP
call (EX_CallMath/EX_FinalFunction/EX_LocalVirtualFunction) this build's VM executes the callee's **Script
bytecode directly** inside ProcessInternal; it only dispatches through Func when NATIVE code calls a BP fn via
ProcessEvent. So Route B's "counter stayed 0" was NEVER a valid negative — the Func-swap just has no effect on
BP->BP calls. **Do not use the Func-swap technique again for BP-invoked functions.**
  NOTE: the native selection handler's OWN calls to IsPreviewable/IsUseable (native->BP, at grid BUILD) would
  go through Func — but the grid was already built (client up for hours), so no build happened in the test
  window; a Func-swap applied EARLY (before first build) MIGHT still catch build-time native->BP calls. Untested
  (needs a relaunch). The Script-bytecode patch works for BOTH paths and is the robust choice.
