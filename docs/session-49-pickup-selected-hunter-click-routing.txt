=========================== THE OPEN PROBLEM (precise diagnosis) =============
Clicking an owned tile:
  - SELECTS the tile (purple highlight) — the click registers as a CommonUI selectable.
  - Does NOT update the center; does NOT fire the native pick (pick_probe: TryPickMyHeroAndCosmetics
    hits=0 on click); does NOT call the leaf predicates I patched (see "what was tried").
WHY the ownership split exists (bytecode, settled): the tile is HeroPickerSelectable_CatalogEntryWith
Preview. IsPreviewable = IsValid(Entry) AND (NOT IsDisabled) AND (NOT CanUse) — TRUE only for UNOWNED
heroes; IsUseable = CanUse (owned). So unowned => previewable => clicking browses into the center;
owned => selectable => routes to the (native) pick, which doesn't complete against our stub.

The native pick chain IS reverse-engineered (in case route A is revisited):
  FName "TryPickMyHeroAndCosmetics" id=0x005904F7; exec thunk +0x54B5380 -> impl **+0x58467E0** ->
  action **+0x5846BE0** (serializes a member-update request body). Impl reads r13=this(PartyManager),
  r15=&HeroAssetId; +0x5846808 call +0x5840730 (members getter -> [rsp+0x40]=data,[rsp+0x48]=count);
  loops members; returns (built-string-len>0). BUT on click it is never invoked, and even when invoked
  it emits NO HTTP (diffed all ags requests), NO WS frame (lobby WS only carries friends/status), and
  no LogLokiPlatformQuery party-write — so the send is gated/deferred and our stub never triggers it.

  Located: IsPreviewable UFunctions @0x26D001D6F00 (CatalogEntryWithPreview tile), @0x26D001D4D00 (base
  HeroPickerSelectable_C); IsPreviewSelection UFunction @0x26CFB237400 (Outer=WBP_HeroPicker_C, id
  0x0079339D). (Heap addrs are PER-RUN — re-derive via findptr each launch.)
RESULT — INERT: patched IsPreviewable->true and IsPreviewSelection->counter. NO center change, and the
counter stayed **0** through 4 MINUTES of the user's real clicks AND a full grid rebuild — even for
IsPreviewable which SHOULD fire per-tile at build. The patch WRITE persists (re-read slot = my stub;
obj Name still IsPreviewable). CONCLUSIONS:
  (1) The traced click chain (HandlePortraitClicked -> "Update Hero Selection" -> IsPreviewSelection ->
      OnHeroSelected) is NOT the runtime path — IsPreviewSelection is never hit on click.
  (2) The tiles don't re-evaluate IsPreviewable in the click/rebuild flow: CommonUI TileView POOLS the
      entry widgets, so "previewable" is computed once at FIRST build (before any patch) and reused;
      filter/re-nav reuses pooled entries.
  (3) I never confirmed the Func-swap actually REDIRECTS (couldn't get a target function to fire), so
      0-counts are ambiguous — VERIFY the swap on a known-hot function before trusting it.
