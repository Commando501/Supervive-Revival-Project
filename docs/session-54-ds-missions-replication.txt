BLOCKER 1 — FMissionProgress ELEMENT WIRE FORMAT DESYNC (the modal can't render yet)
-----------------------------------------------------------------------------------
With 2 missions seeded, the client rejects the property bunch:
    LogRep: Error: ReceivedBunch: Invalid replicated field 0 in LokiPlayerState_Missions ...
    LogNet: Error: UActorChannel::ProcessBunch: Replicator.ReceivedBunch failed.
            Closing connection. RepObj: LokiPlayerState_Missions ..., Channel: 4
then a ~1s connect/fail/reconnect loop (the churn eventually crashed the client too).
ISOLATION TEST — seed 0 missions (both arrays == CDO empty => NOT in the changelist
=> zero element bytes on the wire): the field-0 error VANISHED (grep count = 0), the
connection was STABLE (single Join, PC set, 6 channels, ~103s uptime vs ~1s in the loop).
=> DECISIVE: the desync is the FMissionProgress ELEMENT serialization, NOT the class
   rep layout (RepIndex 11/12 is correct). Our member-wise mirror (using engine
   FPrimaryAssetId/FDateTime) does NOT match the client's FMissionProgress wire format.
   All 9 field TYPES match the usmap, and the engine sub-structs expand identically on
   both ends, so the remaining explanation is that the client's FMissionProgress has a
   CUSTOM NetSerialize (collapses the element to ONE RepLayout cmd) — our member-wise
   struct writes ~11 cmds' worth of bits, the client reads 1 NetSerialize's worth, and
   the cursor desyncs -> the post-property field header reads garbage -> "field 0".
FIX (next session): RE the client's FMissionProgress::NetSerialize byte layout from the
   exe and mirror it as a WithNetSerializer USTRUCT (pattern: FPoolableActorServerState
   in LokiReplicatedStructs.h + Loki.cpp). Confirm the "custom NetSerializer" theory
   first by checking STRUCT_NetSerializeNative in the client's FMissionProgress
   UScriptStruct->StructFlags (live RPM via usmapdump-style walk), or by empirical bit-
   count comparison (instrument the stub to log the bytes it writes for the element).

BLOCKER 1 ROOT-CAUSED + FIXED (2026-07-07, live RE) — usmap was WRONG about a field
==================================================================================
The "custom NetSerialize" theory was FALSE. Live RE of the running client (read-only RPM;
new tools tools/re/struct_probe.py, field_walk.py, rep_expand.py) proved FMissionProgress
is a plain member-wise struct (StructFlags=0x1001, no STRUCT_NetSerializeNative). So is the
client — meaning our member-wise mirror SHOULD have matched. The decisive step was expanding
BOTH sides' FMissionProgress the exact way FRepLayout does (recurse structs lacking
STRUCT_NetSerializeNative(0x400); arrays emit a cmd then recurse Inner) and comparing:
  - STUB (our mirror):   12 leaf cmds  — ObjectiveProgress = TArray<int64> -> [array]+[int64].
  - CLIENT (live truth): 22 leaf cmds  — ObjectiveProgress = TArray<FMissionObjectiveProgress>!
=> THE USMAP + session-52 doc were WRONG: they list ObjectiveProgress as ArrayProperty<Int64Property>,
   but the LIVE client's reflection shows the inner is the struct FMissionObjectiveProgress (8 fields:
   ObjectiveName(FName), Progress(float), MaxProgress(float), Context(TArray<FString>),
   InitialArmoryContext(TArray<FPrimaryAssetId>), StartingProgress(float), Complete(bool), Failed(bool)).
   Our int64 inner made the array element 10 cmds too short -> the client's read cursor desynced right
   after ObjectiveProgress -> the leftover bits parsed as a bogus field header -> "Invalid replicated
   field 0". EVERYTHING ELSE in FMissionProgress already matched (incl. the surprise that FDateTime HAS
   STRUCT_NetSerializeNative(0x400) so Expiry/GrantedAt are single NetSerialize cmds on both sides).

FIX (necessary, NOT yet sufficient): added FMissionObjectiveProgress mirror
(LokiPlayerState_Missions.h) and changed ObjectiveProgress to
TArray<FMissionObjectiveProgress>. The stub's boot RepLayout dumper (Loki.cpp
DumpMissionProgressRepCmds) now reports FMissionProgress = 22 leaf cmds, CMD-FOR-CMD
identical to the client (incl. the nested Context + InitialArmoryContext arrays;
MillisUntilExpiry=[19], Expiry=[20], GrantedAt=[21] on both).

BUT THE LIVE DS RETEST STILL FAILS: "Invalid replicated field 0" persists even with the
22-cmd structure matched. So there is a RESIDUAL bit-level desync beyond the cmd structure.
Localization test (seed 0 objectives => ObjectiveProgress empty, element never serialized):
STILL fails => the residual is in the OUTER FMissionProgress leaves (ID FString, AssetId/
PoolId FNames, MillisUntilExpiry int64, Expiry/GrantedAt), not the MissionObjectiveProgress
element. Ruled out so far (all engine-standard + self-describing, identical both sides):
  - FDateTime: NetSerialize is just `Ar << Ticks` (Core/Private/Misc/DateTime.cpp:201) — 64 bits.
  - FName: UPackageMap::StaticSerializeName is self-describing (1 bit hardcoded-flag, then a
    packed EName index OR FString+int32 Number) — portable across name tables.
  - FString/bool/int64/float: standard self-describing NetSerializeItem.
Since structure matches AND every leaf is self-describing, a pure content/structure desync
should be IMPOSSIBLE — which points to one of:
  (A) CLASS-LEVEL handle misalignment: Missions sits at a RepLayout handle = (AActor rep cmd
      count)+1. If SUPERVIVE's AActor expands to a different cmd count than our stock+injected-
      ServerState AActor, Missions' handle is off. The empty-actor test did NOT expose this
      (Missions not sent when empty; ServerState==CDO also not sent), so it only bites when
      Missions data flows. This is the leading hypothesis.
  (B) A SUPERVIVE engine-level serialization mod (e.g. a modified RepLayout/array-count/FName
      path) not visible in stock UE 5.4 source.
NEXT STEP to resolve: a BIT-LEVEL wire capture — dump the exact bunch bytes/bit-count the stub
writes for LokiPlayerState_Missions, and/or dump the CLIENT's actual FRepLayout Cmds (handles)
for its LokiPlayerState_Missions (needs the client live + RepLayout walk). Compare the Missions
handle + per-cmd bit widths. A stub self-round-trip (serialize then deserialize its own
RepLayout in-process) would also cleanly split stub-bug vs stub-vs-client-diff.

*** WHY THE HUD DOESN'T LOAD — ROOT-CAUSED (2026-07-07, live RE) ***
The main menu is GameMode-driven. On the standalone client the lobby (LVL_LobbyV2_Persistent) runs
GameMode **BP_MainMenuGameMode_C** (log: "Game class is 'BP_MainMenuGameMode_C'" immediately before
"HUD BeginPlay - BP_MainMenuHUD_C"). Its CDO (read live, /Game/Loki/UI/MainMenu/BP_MainMenuGameMode)
specifies the FULL menu class set:
    HUDClass                = BP_MainMenuHUD_C          (/Game/Loki/UI/MainMenu/BP_MainMenuHUD)
    PlayerControllerClass   = PC_MainMenu_C
    GameStateClass          = BP_MainMenuGameState_C
    DefaultPawnClass        = BP_MainMenuPawn_C
    (PlayerStateClass=APlayerState, SpectatorClass=ASpectatorPawn — native)
The HUD + widgets are built client-side by these BP classes (HUD BeginPlay creates WBP_UI_MainMenu_*).
On the DS-connected client the client is a NETWORKED client — it does NOT run a local GameMode; the
SERVER (stub) does, and the travel URL forces `?game=/Script/Loki.LokiStubGameMode`. LokiStubGameMode
: AGameModeBase uses STOCK/DEFAULT classes: HUDClass=AHUD (empty), PlayerControllerClass=APlayerController
(stock), GameStateClass=AGameStateBase, DefaultPawnClass=ADefaultPawn. So the client gets an empty HUD
and a stock PC — none of the BP menu-building logic runs => bare lobby.

FIX FEASIBILITY (why this is a HARD wall, not a quick fix):
  1. All four menu classes are /Game client Blueprints the stub can't load — each would need the
     NetGUID-by-path trick (fake a class at the exact path so the client resolves it to its own BP).
  2. *** The PlayerController is the killer. *** The menu is driven by PC_MainMenu_C, but session 41
     established the stub MUST use STOCK APlayerController — it cannot match SUPERVIVE's modified PC RPC
     signatures (ServerVerifyViewTarget / ClientSetViewTarget), and using the real menu PC breaks the
     connection. In a networked game the client's LOCAL PC == the server's PlayerControllerClass (same
     class, replicated), so we CAN'T give the client PC_MainMenu_C without the stub being it — which the
     RPC-signature constraint forbids. Direct conflict.
  3. Even a HUDClass-only attempt (stub HUDClass -> BP_MainMenuHUD_C via NetGUID-path, cheapest to try)
     may fail: BP_MainMenuHUD_C's BeginPlay likely casts the PC to PC_MainMenu_C / reads
     BP_MainMenuGameState_C, and would get null/stock substitutes.
NET ASSESSMENT: the DS route can CONNECT the client + REPLICATE mission data (both proven), but making
SUPERVIVE's STANDALONE-designed main menu render as a NETWORKED client collides with the client's
architecture AND the session-41 stock-PC constraint. Paths, roughly: (A) HUDClass-only NetGUID-path test
(cheap, likely insufficient); (B) full menu-class emulation incl. PC_MainMenu_C (blocked by RPC sigs);
(C) client-side shim that force-spawns BP_MainMenuHUD_C + builds the menu, decoupled from the networked
GameMode (bypasses the PC constraint but is a client hack); (D) hybrid — keep the client STANDALONE for
the menu and deliver missions another way (but session-52 closed the client-side data channels, which is
what motivated the DS route). This is the crux decision for the DS route's viability.
