1. FMissionProgress USTRUCT — member-wise mirror of SUPERVIVE's FMissionProgress
   (usmap schema.txt:32018, 9 fields, in exact order):
     ID(FString) AssetId(FPrimaryAssetId) PoolId(FPrimaryAssetId) Complete(bool)
     Failed(bool) ObjectiveProgress(TArray<int64>) MillisUntilExpiry(int64)
     Expiry(FDateTime) GrantedAt(FDateTime).
   Uses the ENGINE FPrimaryAssetId / FDateTime types (CoreUObject/Core), so the
   RepLayout cmd expansion is byte-identical to the client's (FPrimaryAssetId -> 2
   FName cmds; FDateTime -> 1 int64 Ticks cmd). Only FMissionProgress itself is
   mirrored; the sub-structs are shared engine types.

2. ALokiPlayerState_Missions : AActor — named exactly LokiPlayerState_Missions so
   its path is /Script/Loki.LokiPlayerState_Missions. Because the SUPERVIVE game
   module is ALSO named "Loki", this path MATCHES the client's real class; when the
   stub exports the actor's class NetGUID by path, the client resolves it to ITS
   OWN class (same mechanism that already gets stock engine classes recognized —
   no IoStore/mod-pak overlay). Replicated props (DOREPLIFETIME, RepNotify):
     Missions              (TArray<FMissionProgress>)   -> RepIndex 11
     FinalMissionProgress  (TArray<FMissionProgress>)   -> RepIndex 12
   bReplicates=true, bAlwaysRelevant=true (menu has no gameplay-relevant position,
   so distance relevancy would never send it). OwningPlayerState is a NON-replicated
   plain UPROPERTY (matches usmap — the client's is a plain ObjectProperty).

3. PostLogin spawn+seed — for each connecting PC, spawn ALokiPlayerState_Missions
   owned by that PC and seed Missions with 2 Armory dailies (PlayAGame, GetKnocks)
   in pool "Daily", with real UtcNow GrantedAt / +24h Expiry timestamps (so the
   client's pool-timer doesn't log "DateTime in bad format (year 0)").

THE OPEN QUESTION (for the live test): CLIENT-SIDE MODEL ASSOCIATION
-------------------------------------------------------------------
The remaining unknown is HOW the client associates the replicated
LokiPlayerState_Missions with the local UMissionsModel (which has a MissionsActor
field, session-52). The usmap shows OwningPlayerState is NOT replicated, so the
client can't use it directly. Candidate association mechanisms, in order of
likelihood, to check against the live client:
  (a) AActor::Owner (which IS replicated) — we spawn owned by the PC, so the client
      receives Owner as a NetGUID. The client's ProgressionManager may bind the
      missions actor whose Owner resolves to the local PC/PlayerState.
  (b) The client scans for any LokiPlayerState_Missions actor and binds the first/
      local one regardless of owner.
  (c) It expects the missions actor as a SUBOBJECT/child of the LokiPlayerState
      (then approach: spawn it attached to / as a component of the now-replicating
      PlayerState instead of a standalone actor).
If (a)/(b) work, the current build renders. If neither fires, next step is to RE the
client's ProgressionManager/UMissionsModel binding (find who sets MissionsModel.
MissionsActor and what it keys on) — session-52 doc has the MissionsModel API and
the CreateMissionsModel(PSMissions) entry point.
