AVENUE A — HOW THE PRIMITIVE WORKS (the reusable recipe)
-------------------------------------------------------
A direct call to a native UFunction's thunk, bypassing ProcessEvent entirely, on the game thread,
using a REAL (captured live) FFrame as the template. Mechanism:
  1. Hook ProcessInternal @base+0x13454A0 (the proven-reliable game-thread hook — pi8 /
     catalog_store_fix all use it every session; it fires constantly at the menu).
  2. In the hook, on the game thread with a valid FFrame arg, CAPTURE that FFrame (memcpy 0x180
     bytes) as a template. It has a valid FOutputDevice vtable @+0 and valid internals, so any
     incidental field read the thunk does is safe.
  3. Build myframe = template with: Node(+0x10)=UFunction, Object(+0x18)=Context(the this),
     Code(+0x20)=NULL, Locals(+0x28)=my buffer.
     - Code=NULL is the key safety trick: for a no-param function the thunk's P_FINISH does
       `Stack.Code += !!Stack.Code` (the observed prologue `mov rax,[rdx+0x20]; xor r9d,r9d;
       test rax,rax; setne r9b; ...`) => reads Code, advances by (Code!=0). With Code=NULL it
       reads 0, advances 0, and NEVER derefs *Code. No bytecode is interpreted.
  4. Call the thunk directly:  ((void(*)(void* Context, void* FFrame, void* Result))thunk)
       (Context, &myframe, &result);
     thunk = UFunction.Func @ UFunction+0xE0.  x64 ABI: rcx=Context, rdx=&FFrame, r8=&Result.
  5. The native body runs and writes its return value to Result. For a getter, Result[0] = the
     returned pointer.

WHY THIS WORKS WHERE ProcessEvent DIDN'T
----------------------------------------
- ProcessEvent (probe2, s54) no-ops for native when called from inside script execution — thunkHits=0.
- A DIRECT thunk call has NO guards: it is just calling the function pointer. Re-entrancy, script
  state, FUObjectThreadContext — none of it matters. The thunk IS the native function's entry.
- The captured live FFrame means we don't have to hand-fabricate FOutputDevice/vtable/internal
  fields — we inherit a valid one and only repoint the 4 fields the thunk needs.

AVENUE B — WHAT HAPPENED (probe3, docs/missions-nativecall3-marker.txt)
----------------------------------------------------------------------
Hypothesis: ProcessEvent no-ops for native only because probe2 called it RE-ENTRANTLY (from the
ProcessInternal hook, mid-script). probe3 hooked ProcessEvent ITSELF (base+0x12C5A10) to sample
native->script boundaries and call the target native from there via the trampoline.
  [2] resolve OK (same ProgMgr/GetMissionsModel/thunk/knownMM as probe4).
  [2] PE first16: 48 89 5C 24 18 55 56 57 41 54 41 55 41 56 41 57  (= mov [rsp+18],rbx; push
      rbp/rsi/rdi/r12-r15 — textbook ProcessEvent prologue; steal-5 was a clean instr boundary).
  [4] DONE. peSeen=0 attempts=0 thunkHits=0 ...  => the ProcessEvent-ENTRY hook NEVER FIRED.
peSeen=0 means OnPE was never entered in the 10s window. InstallJmp reported no failure. Candidate
causes (undiagnosed, since Avenue A mooted it): (a) at an IDLE menu, ProcessEvent at that specific
RVA may be called far less than assumed (much BP execution enters via ProcessInternal/CallFunction
from the tick pipeline, not ProcessEvent); (b) the 5-byte JMP write over the hot ProcessEvent entry
didn't "take" (packer/anti-tamper page handling) despite SafeWrite reporting success. NOT pursued —
Avenue A is the primitive we needed. If ever wanted, probe3 should read-back-verify the installed
JMP bytes and extend the window; but there's no reason to prefer B now.

READING THE INGESTION WIRING (what the widgets consume): the category widgets read
`ProgressionManager.GetMissionsModel()` (== the ProgMgr's OWN live MissionsModel = knownMM) and
subscribe to its OnUpdated. So populating a SEPARATE model (Create*) doesn't help unless it's
assigned back to the ProgMgr / knownMM. The game's real path is: replicated LokiPlayerState_Missions
-> MissionsModel.OnPSMissionsUpdated() rebuilds knownMM's Missions/Pools from its MissionsActor. On
standalone MissionsActor is null. So the S56 crux is getting data INTO the live knownMM. Options to
try (all now executable via Avenue A): (1) call GetMissions() first for the baseline (safe); (2)
re-test CreateMissionModelFromFinalProgress(populated TArray<FMissionProgress>) — if it now returns
non-null, inspect its GetMissions().Num, then find how to make knownMM adopt it; (3) craft/point
knownMM.MissionsActor at a populated LokiPlayerState_Missions then call OnPSMissionsUpdated().
FMissionProgress layout is known cmd-for-cmd from s54 (22 leaves; ID/AssetId/PoolId/Complete/Failed/
ObjectiveProgress(TArray<FMissionObjectiveProgress>)/MillisUntilExpiry/Expiry/GrantedAt).

PARAM-MARSHALLING for Avenue A with params (S56): the Code=NULL trick only covers no-param fns. For
params, either (a) marshal each param into a Parms frame and use ProcessEvent-style property copy
(but ProcessEvent no-ops native), or — cleaner — (b) call the thunk directly with a real captured
FFrame whose bytecode Code stream feeds the params: the thunk reads params by stepping Code via
Stack.Step. Simplest robust route: build a params struct in memory and drive the thunk with a
hand-assembled Code stream of EX_ tokens, OR (easiest for a getter-with-out-params like GetMissions)
keep Code=NULL and read the return TArray from the Result buffer (Result[0]=data ptr, Result[1]=Num).
Start with GetMissions (no in-params, returns TArray) to prove return-by-value works, then tackle
in-params.
