★★★ ROOT CAUSE (usmap ground truth, decisive) ★★★
--------------------------------------------------
The pre-S62 handleCoreGamePlayer returned an INVENTED shape (MatchParticipant + nested
MatchInfo with Address/Port/State/GameMap + ContentService* + legacy hasActiveMatch). The
schema.txt usmap dump shows the REAL model is only 4 fields:

    CoreGamePlayer : (4 props)
        ID               StrProperty
        MatchID          StrProperty     <-- the signal: non-empty == "you have a match"
        Version          Int64Property
        CanDisassociate  BoolProperty

So at the TOP LEVEL of our response, the ONLY field that matched was CanDisassociate(=false).
MatchID was ABSENT -> the client parsed MatchID="" -> "no active match" -> it just kept
polling forever. That is EXACTLY the S61 symptom (response parses clean, zero LogJson errors,
no travel, no NetConnection). The S53 "binary scan" CoreGamePlayer model (MatchParticipant/
ContentServicePrimaryAsset/CanDisassociate) was WRONG — those are fields of OTHER structs, not
CoreGamePlayer. usmap is authoritative for struct field layout; trust it here.

Capture.log proof (this capture IS the S61 session — ags PID/time match): after the single
POST /startSoloMode the client hammered GET /core-game/players 11721x and NEVER hit any match-
details route. It never escalates because MatchID stayed empty. Populate MatchID and it will.

KEY BEHAVIOURAL FINDINGS (all live-verified this session):
1. TRAVEL IS ONE-SHOT AT MATCH ENTRY. The client fires its travel/connect attempt exactly once,
   when it FIRST enters the match, using the ConnectionDetails.address present AT THAT MOMENT.
   - First live entry had address="" (my initial "local tutorial" guess) -> "Attempting to travel
     ... Address:''" -> parked forever in the pre-game lobby (NO local map Browse; the menu route
     does NOT do a local open — it always connects to a server address).
   - Serving the address LATER (hot-swap) did NOT re-fire travel; nor did bumping MatchInfo.Version.
     Only a FRESH entry (address present on the first fetch) fires the connect with the address.

   uses those only to refresh the model — not to re-trigger travel.

   screen; even an empty MatchID on /core-game/players won't evict it. Set true. (Once stuck, only
   a game relaunch frees it — the leave is client-side, no backend release exists.)
4. ConnectionDetails.address is read into the travel as the server host:port ("127.0.0.1:7777").
