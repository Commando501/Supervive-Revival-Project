STATIC RE IS DEAD ON THIS BINARY (calibrated, decisive)
-------------------------------------------------------
Tried to locate UEngine::Browse (and the revert caller) via usmapdump `wstrings` + `xrefstr` on the log format
string "%s Started Browse: \"%s\"" (in-module @0x7FF6BD738940): 0 LEA xrefs. CALIBRATION: xrefstr on a string
from LIVE, currently-running menu UI code ("Applying input config for leaf-most node", in-module @0x7FF6BDB7DB90)
ALSO returned 0 hits. => this packer does NOT reference .rdata strings via plain rip-rel LEA (mutated/virtualized
memory access), so `xrefstr` cannot find function bodies from their strings — for ANY string, committed or not.
This matches S61 ("xrefstr AND findptr = 0 hits" on the Login strings). CONCLUSION: static string->code xref is
not viable here; the revert code cannot be found this way. Future RE must be RUNTIME (in-shim, during travel) or
behavioral, which is how every prior win (roster/store/missions/login/PlayerState) was achieved.

S64 DEEP DIVE (same session, continued) — the revert IS the CoreGameMatchModel-invalid path; PATH 1 needs a
COMPLETE model, not a poke. Live/autonomous (in-shim runtime probes via the object-walk, since static RE is dead).
================================================================================================================
Built a runtime DETERMINATION PROBE into the shim (DumpCoreGameState): walk GUObjectArray for the live
CoreGameManager, dump its match/model/session/server props + the CoreGameMatchModel's own state. Findings:

1. CoreGameManager (cls=CoreGameManager) PERSISTS from the menu. Its CoreGameMatchModel @0x6E0 is NON-NULL
   (a real CoreGameMatchModel) during the tutorial => the flow manager is NOT missing the model. HeroSelectModel
   @0x6E8 also non-null. (So the naive "populate a null model" idea is wrong — the model object already exists.)
2. The CoreGameMatchModel is marked INVALID during the force-open tutorial:
     bIsValid @0x30 = 0        (false)
     MatchState @0x48 = 0      (ECoreGameMatchState::PreHeroSelect0 — i.e., no active match)
     MatchInfo @0xB0 = 0       (null)
     SelfModel @0x60, TeamMembers @0x68 = non-null (CoreGameParticipantModel); TeamSize @0x78 = 1;
     ChampionTeamDetails @0x80 = 0xFFFFFFFFFFFFFFFF; OnUpdated* delegates present.
   (Model field offsets recovered via reflection — reusable for PATH 1.)
3. POKE EXPERIMENTS (tight-loop write to the live model across the tutorial):
   - Poke bIsValid=1 + MatchState=5 (InProgress): the game CRASHED ~2.4s after world-up, BEFORE "Client is ready
     to play" (earlier than the normal revert). => the match model IS read by tutorial-init code (poking it
     changed behavior). Forcing InProgress with a null MatchInfo is inconsistent -> init derefs null -> crash.
   - Poke bIsValid=1 ONLY (MatchState left 0): SAME crash ~1.8s after world-up, before "ready".
   DECISIVE INTERPRETATION: the revert we normally see is the tutorial-init GRACEFULLY handling
   "CoreGameMatchModel invalid" by browsing to the lobby. When bIsValid is forced true, init takes the
   "valid match -> proceed" branch, which reads the INCOMPLETE model (null MatchInfo + PreHeroSelect state)
   and crashes. So the model is load-bearing, and the two branches are: invalid -> lobby (graceful);
   valid-but-incomplete -> crash.
