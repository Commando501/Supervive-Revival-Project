SESSION 71 — DS ROUTE: pawn REPLICATES to the client, but possession/control hits the "client needs a Loki PC" wall
====================================================================================================================
Date: 2026-07-11 (autonomous, log-driven). Continues S70 (loading screen cleared; client spectating live LVL_Tutorial).
Goal: give the local player a CONTROLLABLE pawn (the drop-in gate). RESULT: concrete progress + a well-characterized
wall. The server spawns + possesses a pawn and it REPLICATES to the client (verified in client memory), but the client
does NOT complete possession / control it — because the client's networked PlayerController is a STOCK APlayerController
(the stub can't provide the real Loki PC), and SUPERVIVE's gameplay control layer is tied to the Loki PC.

WHAT WAS DONE (unreal-stub/Source/Loki/)
----------------------------------------
- LokiNetDriver::IsClassNetCacheDivergent: UN-SUPPRESSED ADefaultPawn. Live RE (tools/re/rep_expand_full.py on the
  running client) proved the client's APawn = 3 STOCK net props (RemoteViewPitch, PlayerState, Controller) and
  ADefaultPawn = 0 — NO schema divergence (the S38 DefaultPawn suppression was a blanket precaution). So a stock
  ADefaultPawn replicates cleanly.
- LokiStubGameMode::PostLogin: spawn ADefaultPawn at (0,0,500) + bAlwaysRelevant=true + NewPlayer->Possess(pawn) +
  a deferred (3s) ClientRestart re-send. Server-side possession is solid: PC->GetPawn()=DefaultPawn_1, PC
  hasConnection=1, pawn Role=Authority, bReplicates=1.
- LokiStubGameMode::InitGameState: GS->GameModeClass = nullptr. (See finding #1.)

FINDINGS (in order)
-------------------
1. GameModeClass NetGUID blocking-load (FIXED). AGameModeBase::InitGameState set GS->GameModeClass = LokiStubGameMode,
   a class the CLIENT doesn't have. Replicating it made the client spam "LogNetPackageMap: Error: GetObjectFromNetGUID:
   Forced blocking load ... /Script/Loki.LokiStubGameMode" — a SYNCHRONOUS blocking load in the netdriver receive path.
   Nulling GameModeClass removed it (0 errors after). (It was NOT what blocked the pawn — see #2.)
2. The pawn REPLICATES to the client (verified). The client Loki.log never LOGS replicated pawns, so "no DefaultPawn in
   the log" was misleading. Live RPM (tools/re/obj_by_class.py — new, takes the ASLR base as an arg) found TWO real
   DefaultPawn instances + the LokiPlayerState_Missions actor + the LokiGameState on the client. So DS actor
   replication delivers the pawn actor fine.
3. ★ THE WALL: the client does NOT possess/control the pawn. No ServerAcknowledgePossession, no ServerMove, no
   ServerCheckClientPossession come back from the client (checked the stub log) — i.e. the client is not sending any
   possession/movement RPCs. ClientRestart was sent TWICE (at Possess + a 3s deferred re-send) with a valid connection;
   the client still doesn't take the pawn. ROOT: the client's networked PlayerController is a STOCK APlayerController
   (the stub uses PlayerControllerClass=APlayerController — S26 revert; it CANNOT use the real Loki PC because its
   SUPERVIVE-modified RPC signatures break the connection, S41). SUPERVIVE's gameplay possession/input/camera is tied to
   the client's Loki PlayerController (BP_LokiPlayerController_C / its native base, with DropPlaneComponent etc. — seen
   in the client's class list), which the stock networked PC is not. So the pawn arrives but the client's gameplay layer
   never controls it. This is the SAME class of wall the missions-DS route hit (needs Loki PC / PC_MainMenu_C) and the
   force-open route hit (S63: client wants the REAL Loki PC).

SCOPE REALITY — the actual hero pawn
------------------------------------
The tutorial hero is BP_HERO_<X>_C : LokiHeroCharacter/LokiCharacter (native, 182 replicated-eligible props) : Character
(44) : Pawn : Actor, with a LokiCharacterMovementComponent (218 props, CUSTOM movement-prediction NetSerialize).
Mirroring that cmd-for-cmd for the DS route is an ENORMOUS effort (character movement replication is the hardest UE
netcode to reproduce byte-identically). A DefaultPawn was the tractable stand-in to prove the pipeline — which got as
far as actor replication but not control.

character pawn. Neither route can currently give the client a Loki PC without breaking the connection (S41), and the
hero character is a huge replicated schema. Options for next session:

     replicated pawn. Combine with a CLIENT-SIDE shim (the S55 game-thread native-call primitive) to make the client's

     the force-open route lacked (a valid server session), so the client-side possess may now stick.
  B. Provide a Loki PlayerController on the stub via schema-injection of its modified RPC signatures (the S41 wall) —

  C. Full LokiCharacter + movement-component mirror (enormous; movement NetSerialize is the crux).
  D. Accept "client in the live tutorial world (spectator, valid GameState, pawn replicated)" as the practical ceiling
     of the reasonable-effort DS route and document it as the milestone.

real uncertainty (client-spawned heroes need server-authoritative ability/stat/PlayerState init). This is the SAME

uncertain shim effort; it is NOT a quick unlock. HONEST CEILING of the reasonable-effort DS route = "client is in the
LIVE tutorial world with a valid GameState + primed world (spectator)".
