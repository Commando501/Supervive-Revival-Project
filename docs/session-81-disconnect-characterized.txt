## ONE-PARAGRAPH RESULT
S80 handed off believing "the client disconnects from the DS stub ~2 minutes after
every join" and that the S81 wall might be "the DS route cannot hold a connection."
BOTH ARE FALSE. A clean, NO-INJECTION tutorial session held the connection for
17+ MINUTES (still in LokiGameState, healthy game thread, no timeout). A deliberate
20-SECOND game-thread FREEZE (clean SuspendThread) did NOT drop it either. The drops
S80 saw are caused by what MODE_PLAYABLE *does*: it spawns+wires a hero, enables
movement (GetMaxSpeed 0->500, reproduced), then drives per-frame WASD — and the
game's own CharacterMovementComponent tick then blocks the GAME THREAD on a ~20s
KERNEL WAIT (ntdll NtWaitForSingleObject-class), which trips the 15s netdriver
timeout -> ConnectionTimeout -> travel to LVL_Login?closed -> main menu. The DS
route is fine; the movement path is the bug.

## THE DROP MECHANISM (nailed with the live sampler — the whole point of building it)
The gt_sampler.py stream through experiment 3's freeze window (epoch 1784278878..903
== log 09:01:17..09:01:42, the 25s ending exactly at the drop):
  * 96/100 samples: RIP pinned in **ntdll.dll** (offset ~0x9DF14, a
    NtWaitForSingleObject-class KERNEL WAIT), RSP pinned at 0x6032BDF4D8.
    => the game thread is BLOCKED ON A WAIT, not busy-looping. (During experiment-1
    idle it also waits ~80% but in the FRAME-PACING path; here it's a DIFFERENT
    caller ending in the same generic ntdll wait.)
  * 80%-consistent EXE caller chain (the blocking stack), all in the CHARACTER-
    MOVEMENT code region:
      +0x5512397 +0x555D723 +0x56CEA46 +0x56CC961 +0x544CF74   (0x54x-0x56x =
        LokiCharacterMovementComponent region: GetMaxSpeed@0x55ACB90,
        MoveForward@0x569A1B1 both live here)
      +0x33AAE10 +0x33962F2 +0x3396280 +0x33A3D31 +0x338C9FE +0x3383236  (0x33x =
        tick/movement-component tick region)
      +0x137A64F +0x1225FD6 +0x1221597 +0x13453A5  (UWorld/UObject tick +
        ProcessInternal region — ProcessInternal is base+0x13454A0)
  * **+0x3BCC310 (AddMovementInput, per the marker) present in 41% of freeze samples**
    -> the per-frame WASD path is what drives into the wait.
CONCLUSION: enabling movement on the locally-spawned hero + driving per-frame input
makes the game's CMC tick (PerformMovement / a physics sweep or a render/scene
sync it triggers) BLOCK the game thread ~20s on a kernel object -> netdriver
timeout. Prime suspect = a physics-scene lock or a FlushRenderingCommands-style
game->render fence that hangs because the hero is a LOCALLY-spawned actor in a
networked world whose physics/render state isn't what the movement code expects.
NOT yet pinned to the exact sync object (would need an ALL-THREADS minidump during
the freeze to see which thread holds the lock — dump_all_threads.py is ready for it).

## ALL-THREADS MINIDUMP DURING A 2ND FRESH FREEZE (this session — narrows the wait)
Relaunched the client (pid 29544, gameTid 0xCE2C), re-injected PLAYABLE (hero + GetMaxSpeed
=500 reproduced again), and caught the freeze with a log-quiet detector that fired ONE
MiniDumpNormal (tools/re/minidump.py + freeze_dump.sh); analyzed with tools/re/dump_rips.py.
RESULT: the game thread (0xCE2C) sits in **ntdll+0x9DAB4** (a wait). Of ~123 threads, the
only "busy" (non-ntdll/kernelbase/win32u) ones are ALL inside **runtime.dll** — the game's
67MB packer/anti-tamper runtime (\Loki\Binaries\Win64\runtime.dll, mapped twice) — and one
in ws2_32 (the network recv). **ZERO threads are executing in Chaos physics, D3D12/D3D12Core,
or nvwgf2umx (the NVIDIA render driver).** => the game thread is NOT waiting on a physics or
render thread that's actively crunching; it's a LOCK or a TIMED wait (the ~15-20s duration
varies session-to-session, consistent with a resource that frees on a variable schedule or a
wait-with-timeout, NOT a fixed watchdog). Packer note: `runtime.dll` masks the true callee of
those worker threads and the game thread's own stack didn't resolve to exe frames in the dump
(MiniDumpNormal + packer redirection) — the CLEAN movement-chain evidence is from gt_sampler
(above), not the dump. Also: after the 2nd drop the client cleanly EXITED (RequestExit @
09:17:05) — travelling to the menu with PLAYABLE's per-frame vtable hook still installed
(now pointing into the torn-down tutorial world) likely faulted the next frame. So a durable
PLAYABLE must UNINSTALL its hook on NetworkFailure/travel.

## WHY A REAL FREEZE DROPS BUT A SUSPEND DOESN'T (reconciliation)
Experiment 2 (suspend) leaves the game thread frozen but the server keeps sending;
on resume TickDispatch drains the buffered packets and resets the receive timer ->
no timeout. Experiment 3's freeze is INSIDE a frame holding the movement/physics
path; the connection's "Real" (time since last GOOD packet) climbs to 20s and the
first tick after the wait sees >15s -> timeout. (The prior S80/this-morning drops —
frame [843] stuck 20s with feature-toggle spam, Real 20.54, DriverTime 97/102/111/
270/720s — are the SAME mechanism; the variable DriverTime = when the movement/
hero path first hits the blocking wait, which depends on session activity.)

## NEW REUSABLE TOOLS (this session)
* tools/re/gt_sampler.py <pid> <out> [secs=800] [hz=3] [gameTid=0] [exeBase=0]
    Single-thread SAMPLING profiler. Suspends ONLY the game thread a few ms/sample
    (invisible to the anti-tamper, which hooks thread CREATION only), captures RIP+
    stack, resolves EXE frames to +RVA, writes a module map header. Auto-detects the
    game thread = earliest-created thread (verified: tid == the shim's gameTid). This
    is the keystone: it turns a silent freeze into a named blocking call chain.
* tools/re/gt_stall.py <pid> <secs> [gameTid]
    Suspends the game thread N seconds (controlled-freeze experiment). Proved a pure
    stall does NOT drop the connection.
* tools/re/sample_analyze.py <samples.txt> [tail_n]
    Ranks EXE frames in the freeze window. NB: trim by EPOCH correlation, not the
    "last N" — the sampler runs past the drop into the menu, so the tail is menu-idle,
    not the freeze (epoch->log offset: gt_stall's resume ts maps to the log gap end).
