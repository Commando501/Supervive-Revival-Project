1. THE TWO ROOT CAUSES (the S82 "next steps" were both wrong turns)
--------------------------------------------------------------------------------
S82 proposed: (A) open the tab and hope the widget populates, or (B) RE the populate's args and
force-call 0x57DF4B0. (A) was tested and FAILED — the tab was opened 3x with Levels still 0.
(B) is actively dangerous (see §3). The real chain, fully RE'd from the bytes:

`CheckAccountPassChanges` (0x5794480, rcx=BattlepassViewManager) is the populate's REAL caller:
   mov rsi,rcx                                  ; ONLY rcx is an input
   mov rcx,[rsi+0x1C8]                          ; PM = ViewManager+0x1C8
   call 0x5840700  ; GetAccountTrack -> byte[PM+0x208]     test al,al / je bail   <-- GATE A
   call 0x584B920  ; tier predicate: cmp dword[track+0xEC],-1 ; setne al / je bail <-- GATE B
   call 0x562BC70  ; -> X = LokiAssetLoader          test rax,rax / je bail
   call 0x562BED0  ; -> P = HuntersJourney_C (class) test rbx,rbx / je bail
   call 0x53283E0  ; cached UClass (IsChildOf validate) / je bail
   mov rax,[rcx] ; lea rdx,[rsp+0x48] ; call [rax+0x1D0]   ; P->GetPrimaryAssetId(&out)
   mov rcx,rax   ; lea rdx,[rsp+0x38] ; call 0x12F4230     ; FPrimaryAssetId::ToString -> FString K
   mov rdx,rax   ; mov rcx,rsi        ; call 0x57AB180     ; FindVM(ViewManager, K)
   test rax,rax ; je 0x5794670                             ; *** NOT FOUND -> SKIP THE POPULATE ***
   lea r8,[rbp+0xB8] ; mov rcx,rax ; lea rdx,[rsp+0x28] ; call 0x57DF4B0   ; the populate

BLOCKER 1 — TIER GATE. Live-measured: byte[PM+0x208]=1 (Gate A passed, from the S82 /progression
  lever) but dword[PM+0x90+0xEC] (CurrentTierIndex) = **-1** => Gate B failed => CheckAccountPassChanges
  bailed before the populate. The shim writes it (=0).
  *** CORRECTION (post-session RE workflow) — THIS WAS NOT THE CAUSE OF THE EMPTY GRID. ***
  The marker reads `Levels via CheckAccountPassChanges: before=86 -> after=86`: Levels was ALREADY 86
  BEFORE the force-call. The grid is built by the VM BUILDER's unconditional Init `0x57BB560`
  (`+57BB64F mov [rsi+0x70],edx` = LevelsToDisplay; `+57BB65E call 0x57B1130`), invoked from the account
  builder at `+57CABBD` AHEAD OF BOTH GATES, during the adoption broadcast. So BLOCKER 2 (the key) is
  the SOLE verified cause; fixing the key made the builder run for a properly-keyed VM and it populated
  Levels itself. **Whether the tier write is needed AT ALL is UNVERIFIED** — it may be inert for the
  grid (it still matters for progress, see §5d). Cheap test on a fresh launch: set the tier back to -1
  (`battlepass_pm_probe.py --set-tier -1`), bump Version, re-inject, and see if Levels still reaches 86.
  Do NOT repeat the S83 claim that this was "root cause 1" until that test is run.

BLOCKER 2 — ★ THE KEYSTONE: VM MAP-KEY MISMATCH.
  The lookup key is P's stringified FPrimaryAssetId. Live-resolved: **K = "ProgressionTrack:HuntersJourney"**.
  Our shim keyed the VM by the adopted track's ProgressionTrackID = bare **"HuntersJourney"**.
  Live proof of the mismatch (the two maps even use different key TYPES):
     BattlepassViewModels @+0x58 : key = FString          'HuntersJourney'          Levels=0  (ours)
     MasteryViewModels    @+0xA8 : key = FPrimaryAssetId  HeroMastery:Beebo         Levels=9  (works)
  => FindVM missed => `je` => populate skipped => empty grid.
  FIX: resolve K at runtime and set ProgressionTrackID = K BEFORE adoption, so the game INSERTS the
  VM under K. Patching the stored key string in place would NOT work — a TMap find HASHES the key.
  Once keyed correctly the game did the rest natively: it populated Levels AND set LevelsToDisplay.
